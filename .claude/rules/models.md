# Data models (`models/`) & the schema-save gotcha

*Loads when you touch `models/**`. The universal "declare the field in the schema or it silently won't persist" rule also lives in root CLAUDE.md's invariants.*

## Database schema gotcha
Mongoose only persists fields **declared in the schema**. Several past bugs were exactly this: code setting `doc.someNewField = x; await doc.save()` where `someNewField` was never added to the Mongoose schema — it looked like it worked (in-memory) but silently reverted on the next fresh fetch. **Whenever you add a new field anywhere in the codebase, add it to the corresponding schema in `models/` in the same change**, or it will not actually save.

## Data models (`models/`)
- `SeasonalData.js` — one global document (`docType: 'global'`). Holds `currentSeasonTitle`/`bpTitle`/`rankTitle`/`dmzTitle`, `bpEnd`/`rankEnd`/`dmzEnd` (each paired with a `${field}TBD` boolean, live + draft — added 2026-07-31 14:00 EDT, see design-decisions.md), `patchNotes[]` (title = season # & name, NOT "Balance Changes for..." — see patchnotes.js), `newDraws[]`/`returningDraws[]`, `calendar[]` (with `endDate`/ `isOngoing` for "All Season" events, plus **`category`** — `'draw'|'event'|'playlist'`, default `'event'`, added 2026-07-31 12:10 EDT for the 3-section calendar redesign; set via the bulk parser's `d•`/`p•`/`e•` prefix or the single add/edit modal's Category field — see `.claude/rules/design-decisions.md`), and `drawsBannerUrl`/`eventsBannerUrl`/`playlistsBannerUrl` (added 2026-07-31 17:20 EDT — one optional per-page banner image for `/calendar`, re-hosted via `utils/calendarBannerCache.js`, blank = show nothing; see that file + `commands/manage.js`'s "Banners" action).
  - **`draft` (added 2026-07-30 22:24 EDT)** — a next-season staging sub-document mirroring `currentSeasonTitle`/`bpTitle`/`rankTitle`/`dmzTitle`/`bpEnd`/`rankEnd`/`dmzEnd`/`newDraws[]`/ `returningDraws[]`/`calendar[]` (no `patchNotes` — that already has its own overlap-safe "Add New Season" flow). Exists because this whole document is a SINGLE global doc — editing next-season data directly during the overlap window between "current season not over" and "new season announced" immediately overwrites what's live. `/manage` → "Next Season Draft" stages into these fields; "Promote to Live" (`handlers/manage/season.js`'s `handleDraftButton`, the `mng_draftpromoteconfirm` branch) copies them onto the top-level fields in one save and clears the draft — see `.claude/rules/manage-panel.md`.
- `UserPreference.js` — per-user. `seasonalVisibility` is a **shared** toggle covering `/season end`, `/draws`, `/patch notes`, `/calendar`, `/draw prices` together (Option A design decision — see `.claude/rules/design-decisions.md`). `timestampVisibility`, `settingsVisibility`, `defaultRegion`, `loadoutVisibility` are each independent. `calendarEventFilter` (`'active'|'all'`, default `'all'`) backed `/calendar`'s "Show Active Events Only"/"Show All Events" filter, briefly living as a `/settings` Preferences toggle (2026-07-31 → 2026-08-15) — **SILENCED 2026-08-15 13:01 EDT** (Harkirat's direct request): the `/settings` toggle is commented out, nothing reads or writes this field anymore, `/calendar`'s own `view` slash option is the sole (one-off, unsaved) way to pick it now, and every existing stored value was cleared via `scripts/clearCalendarEventFilter.js`. Field kept in the schema, not deleted, in case the preference returns. `accentColorStyle` (`'avatar'|'banner'|'preset'`, default `'preset'` — flipped back from `'avatar'` 2026-08-08 00:24 EDT, see `.claude/rules/accent-and-colors.md`; `'default'` is the old value name for `'preset'`, still treated identically) plus the independently-cached `avatarColorHex`/`avatarColorSource` and `bannerColorHex`/`bannerColorSource` pairs back the accent color system — see `.claude/rules/accent-and-colors.md`.
- `Loadout.js` — weapon loadouts, `mode: 'MP' | 'DMZ'` (MP max 5 attachments, DMZ max 9). `description` (optional flavor text) and `shareCode` (the actual copyable in-game Gunsmith code) were added during the builds.xlsx migration — see `.claude/rules/loadouts.md` for why `shareCode` is separate from `buildName` despite `/manage`'s modal labeling the latter "Build Name / Share Code". Has a compound index on `{ category: 1, mode: 1 }` — every autocomplete keystroke and every `/<category>` command filters on this pair together; harmless at the current collection size (~100-200 docs) but cheap to add ahead of it actually mattering.
- `BotInstance.js` (added 2026-07-25) — lock doc backing the startup single-instance guard, one PER BOT TOKEN (`_id` = a hash of `BOT_TOKEN`, not a fixed singleton -- a production bot and a separate test/dev bot application must be allowed to run simultaneously even against the same Mongo cluster). `hostname`/`pid`/`startedAt`/`lastHeartbeat`, refreshed on a 10s interval by whichever process holds a given token's lock. See `utils/instanceLock.js` and `docs/ROADMAP.md`'s "Single-instance guard" entry for the full mechanism.
- `CollectibleCatalog.js` (added 2026-08-15 10:44 EDT) — runtime Mongo mirror of `docs/reference/nameplate-decoration-catalog.json`, ONE DOCUMENT PER SKU (flattened out of the JSON's collection→group→variants nesting by `scripts/syncCatalogToMongo.js`, additive/idempotent). The JSON stays the git-diffable source of truth; this collection is a derived index built from it, indexed by `sku_id`, so `scripts/bulkCacheCollectibles.js` never re-parses the 480KB file. Full field set: `skuId` (unique), `kind` (`'nameplate'|'decoration'`), `parentCategory`, `groupName`, `baseSkuId`, `asset`, `label`, `name` (raw), `displayName` (computed), `palette`/`paletteHex` (nameplate only), `variantLabel`/`variantValue`, plus this bot's OWN bulk-cache progress tracking (`cacheStatus: 'pending'|'cached'|'failed'`, `cachedAt`, `lastAttemptAt`, `lastError`). ⚠️ **The field is `parentCategory`, not `collection`** — Mongoose reserves `collection` as a schema pathname (it shadows `Model.collection`, the real MongoDB collection handle) and warns that using it "may break some functionality"; caught by that warning on this model's first real query. Compound index on `{kind, cacheStatus}`. See `docs/reference/nameplate-decoration-catalog.md` for the full pipeline this feeds.
- **`AnalyticsEvent.js` · `SearchTerm.js` · `BootRecord.js` (added 2026-08-16 13:24 EDT, v3.35.0-pre)** — the observability layer's **event plane**, written by `utils/eventStore.js`. Design: `docs/superpowers/specs/2026-08-16-observability-layer-design.md` §2, frozen.
  - `AnalyticsEvent` is ONE DOCUMENT PER INTERACTION: `userHash`, `guildId`, `context`, `installType`, `isAdmin`, `command`/`subcommand`, `entry`, `customIdPrefix`, `outcome`, `ackMs`, `durationMs`, `deps[]`, `detail{}`, `search{}`, `version`/`commit`/`host`/`createdAt`. 🔴 **The raw Discord user ID never enters it** — `userHash` is `HMAC-SHA256(ANALYTICS_HMAC_KEY, discordId)` via `utils/requestContext.js`'s `hashUserId()`, the SAME function the diagnostic plane uses, so the two correlate; a second hashing implementation would silently stop correlating with every log line already written. `guildId` IS raw, deliberately — a server is not a person. `scripts/eventStore.test.js` string-searches a finished document for the raw id, and `buildEventDocument()` scrubs against it at runtime with the same predicate.
  - ⚠️ **DELIBERATELY ONE INDEX** (`{ createdAt: -1, command: 1 }`, plus `_id`). This database's own indexes measured **1.7× its data**, the cluster is a free-tier M0 with a 512 MB hard cap, and this collection is designed to grow forever — so index count is the single biggest lever on when the ceiling arrives. Derive any new index from a query the panel or report script actually runs; never add one speculatively. A `userHash` lookup collection-scans on purpose (rare, manual, and an index for it would be paid on every write forever).
  - `SearchTerm` is the alias-design surface and carries **no user linkage at all** — `{ term, command, field, searches, zeroResults, picked, firstSeen, lastSeen }`, upserted per closed search session. The term is normalised and capped at 100 characters before it gets here.
  - `BootRecord` is one row per process start and holds nothing about any user. ⚠️ **It is also where restart COUNT comes from** — `process.uptime()` reports the current process's age and cannot know how many times systemd restarted the unit.
  - 🗑️ **These replaced `RenderTiming`**, which stored a **raw** `discordId` and was deleted in the same change along with `utils/renderTiming.js` (migration: `scripts/migrateRenderTimings.js`). Its `/colors` fields now ride in `detail` via `eventStore.mergeDetail()`, and the two WebP caches report through `recordRenderTiming()`. If you find a reference to `models/RenderTiming.js` anywhere outside the record files and the frozen design spec, it is stale.
