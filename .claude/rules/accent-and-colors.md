## Accent color system (`utils/accentColor.js`, `utils/colorExtract.js`)
Discord's legacy `accent_color`/`hexAccentColor` user field is only populated for accounts with **no banner set** (the client shows one or the other) — it comes back `null` for almost every active user. Discord's newer Nitro name-color feature (`display_name_styles.colors`) IS exposed over the bot API as of the current version (v10) — see the `'displayName'` style below — but avatar/banner/decoration/nameplate have no Discord-provided color value at all, so those four are extracted ourselves:
- `colorExtract.js`'s `getDominantColor(url)` downloads an image (avatar or banner) via `jimp`, samples ~2500 pixels, and picks a representative hex value — see "Accent color extraction algorithm" below for exactly how (it's gone through 3 real revisions, not a simple average).
- **`'preset'` (Pre-Designed Palette) is the actual default again** (`accentColorStyle` schema default flipped back to `'preset'` 2026-08-08 00:25 EDT, per Harkirat's direct request — this reverses the 2026-07-13 flip to `'avatar'` below). Applies to new users and anyone who hasn't explicitly saved a style preference yet; anyone with an existing saved `'avatar'`/`'banner'`/etc. doc is completely unaffected, since a schema default only ever fills in a value that was never set. `/settings` itself has no brand color of its own so it still falls back to avatar even under `'preset'`. ~~Avatar-matching is the actual default (Harkirat wanted every embed to match a user's avatar out of the box, not just `/settings`)~~ — **superseded.** Re-confirmed 2026-07-18 that this was the OPPOSITE of Harkirat's own mental model ("defaults to the pre-made palette unless changed"); left as `'avatar'` at the time with no action taken, then actually flipped this session.
- `accentColor.js`'s `resolveAccentColor()` resolves `prefs.accentColorStyle` accordingly, and `getAccentColorForCommand()` is what the 5 preset-color commands (calendar/draws/ patchnotes/drawprices/seasonend) call. **It now creates-and-saves a `UserPreference` doc if the user doesn't have one yet at all** — before this, only `/settings` ever created that doc, so a user whose first-ever interaction was e.g. `/calendar` would have `prefs === null`, and the whole accent system (including the schema default) would silently never engage until they happened to run `/settings` first. Only `'preset'` skips the Discord user-object fetch; `'avatar'` (now the common case) always resolves+caches.
- Avatar and banner colors are cached **independently** on `UserPreference` (`avatarColorHex`/`avatarColorSource`, `bannerColorHex`/`bannerColorSource`) — a user might switch back and forth between styles, so both get remembered rather than invalidating one when the other changes. Each `*Source` field is the Discord image hash the cached hex was computed from; a fresh CDN download + re-extraction only happens if that specific image actually changed. **Caching is keyed on the image hash, NOT on the extraction algorithm version** — changing the algorithm (see below) does nothing for a user's already-cached color until their underlying avatar/banner image changes, or the cache is manually cleared.
- **`/settings`' one exception is `'preset'` specifically, not "always avatar."** If a user's `accentColorStyle` is explicitly `'banner'`, `/settings` correctly shows their BANNER color (falling back to avatar only if they have no banner uploaded at all) — `resolveAccentColor()`'s `defaultBehavior: 'avatar'` param (which `/settings` passes) only overrides the `'preset'`/`'default'` case, since that's the one style with no brand color to show at all. Don't read "`/settings` falls back to avatar" as "`/settings` always shows avatar regardless of style" — it doesn't.

### ✅ RE-EXAMINED AND KEPT 2026-08-11 19:09 EDT — the accent algorithm does NOT inherit the palette rewrite, and the measurement says so
Harkirat's question after a day of extractor work: the accent colour is derived differently from the palette, so verify that, then decide whether to keep it or fold today's improvements in. **Verified — it is entirely HSL-based** (24 hue bins on HSL hue, `s < 0.15` / `l > 0.92` / `l < 0.08` filters, `weight = s²`, and a `vivid` score of `s × lightness-centering`), while the palette moved to two-pool OKLab with farthest-first seeding. It therefore *does* carry the same HSL-saturation flaw the label layer was fixed for — `#FDFEFE` reports `s` = 0.333.
- **Kept anyway, on evidence.** Across the 11-image corpus the current accent lands a mean **ΔE 0.037** from the nearest real palette swatch, and **10 of 11** are within `MERGE_DELTA_E` (0.07) — i.e. the tint the user sees on an embed is almost always a colour `/colors` actually shows them. It is not the broken thing the HSL flaw predicts.
- 🚫 **A chroma-based rewrite was built and REJECTED on its output** — the same fix that was right for the labels is wrong here. Swapping every saturation judgement for OKLab chroma changed **6 of 10** images visibly (mean ΔE 0.112), and the changes ran in exactly the direction already on file as a complaint: `cinnasip.png` went `#FAC5C0` (pale pink) → **`#4D5395`** (ΔE 0.423) — the dark navy the over-saturation item is about — and `PandaBobba.png` went `#FF98CE` → `#E03495`. **One image returned NO colour at all**, because the chroma floor excluded every pixel, dropping it to the plain-average fallback.
- 📐 **The insight worth keeping: HSL's inflated saturation at high lightness is, for THIS job, a feature.** It biases the accent toward light, prevalent colours — which reads as representative for an avatar tint — where chroma biases toward small, punchy regions. The palette layer *wants* the punchy tail (that is what surfaces a cat's red eyes); a single embed tint does not. **Same flaw, opposite correct answer.** Do not "finish the job" by porting the chroma fix here.

### Accent color extraction algorithm (`colorExtract.js`'s `getDominantColor()`)
Gone through 3 real revisions, each found wrong by testing against Harkirat's actual Discord avatar rather than a hypothetical:
1. **Flat average of every sampled pixel** (original) — washed out toward gray/white for the common case of a mostly-pale avatar with one small vibrant feature.
2. **Saturation-weighted average** (2026-07-12) — down-weighted low-saturation background pixels correctly, but still averaged RGB across genuinely DIFFERENT hues (e.g. teal hair + skin tone) into a muddy blend that could look like none of the actual colors present.
3. **Dominant hue-cluster + vivid bias, "vivid"** (2026-07-13, current) — buckets sampled pixels into 24 hue bins (15° each), excluding near-neutral pixels (low saturation, or blown-out near-white/near-black) entirely from consideration; the bin with the highest saturation²-weighted total wins; the final color averages only the TOP 20% most vivid pixels within that winning bin (ranked by saturation and mid-range lightness), not every pixel in it — biased toward the punchiest instance of the dominant hue rather than its overall muted average. Confirmed live by generating a side-by-side artifact (real Discord-embed mockups: 4px accent strip + `#131416` body) comparing all 3 algorithms against Harkirat's own avatar plus 4 other real test images (a gradient orb, a holographic photo, an animated GIF, a cartoon screenshot) before picking this one. **On an image with multiple comparably-saturated but unrelated hues, this favors the MORE saturated hue even if a less-saturated one covers more area** — confirmed intentional (checked the raw per-bin weight data directly on the gradient-orb test case: a small vivid-blue region legitimately outweighed a larger but less-saturated coral region), not a bug to fix.
- Applies identically to BOTH avatar and banner extraction — they share this one function (`accentColor.js`'s `getCachedColor()` calls it for both `kind: 'avatar'` and `kind: 'banner'`), so no separate banner-specific logic exists or is needed.
- **Every user's cached `avatarColorHex`/`avatarColorSource`/`bannerColorHex`/ `bannerColorSource` was cleared (2026-07-13)** after shipping the vivid algorithm, so every user's color recomputes fresh on their next accent-color-resolving command instead of silently keeping a stale pre-vivid value indefinitely (per the image-hash caching note above). One-time `UserPreference.updateMany({}, {$unset: {...}})` — not a recurring migration, don't re-run it reflexively on future algorithm tweaks without thinking through whether that specific change actually invalidates existing cached values.

### Post-click latency fix (2026-07-13) — `getAccentColorForCommand()` no longer force-fetches
for avatar style Real, user-reported hesitation between a button's Discord-side "loading" spinner ending and its content actually updating, traced to `getAccentColorForCommand()` unconditionally calling `interaction.client.users.fetch(id, { force: true })` on every single call — a forced Discord REST round-trip on every pagination/toggle click regardless of whether the color cache was about to hit. Fixed: only `'banner'` style still force-fetches (banner data genuinely isn't in the lightweight interaction payload); `'avatar'` style (the default at the time this fix shipped — see the flip back to `'preset'` above) reuses `interaction.user` directly. **Confirmed safe via discord.js source itself** (`BaseInteraction.js`/`CachedManager.js`/`User.js`): Discord sends the clicking user's live avatar hash with every interaction, and `_patch()` always overwrites `.avatar` from that payload, so a different user clicking a shared message, or the same user changing their avatar between clicks, both still resolve correctly with zero extra fetch. Banner has no equivalent free signal (a structural API difference, not an oversight), so it keeps a throttled force-fetch instead: `bannerRecheckCache`, `RECHECK_WINDOW_MS = 15 * 60 * 1000` — a real slash-command invocation (`interaction.isChatInputCommand()`) always bypasses the window and fetches fresh (confirmed via `buildSyntheticInteraction` (utils/interactionContext.js) that a button-driven re-render correctly still reads `isChatInputCommand() === false`, since the synthetic interaction preserves the original component interaction's `.type`); only button/select re-renders of an already-open message consult the 15-minute cache. This adds zero latency to `'preset'`-style users (returns `presetHex` before any of this runs) or `'avatar'`-style users (never fetches at all) — only `'banner'`-style users' fresh slash-command runs pay the force-fetch cost, same as before this fix, just scoped correctly instead of hitting every render.

### 'displayName' style — Discord's real Nitro name-color gradient (2026-07-13)
Discord exposes a genuine 2-stop name-color gradient a user explicitly picked via their own UI: `display_name_styles.colors` (an array of 2 decimal RGB ints, e.g. `[7183099, 6082490]` → `#6D9AFB`/`#5CCFBA`). **Not parsed by discord.js's own `User` class at all** — confirmed against the installed v14.26.4, `User._patch()` has no handling for it whatsoever (unlike `collectibles`/`primary_guild`, which it DOES parse — this field is simply newer than what this discord.js version implements), so even a force-fetched `client.users.fetch()` silently drops it. The only way to read it is a raw REST call that bypasses the User model entirely: `client.rest.get(Routes.user(userId))` — same `client.rest` object every V2 command already uses for `rest.patch('@original')`, just a GET. `accentColor.js`'s `fetchProfileExtras(client, userId)` is this one raw call, shared by the `'displayName'`/`'dynamicProfile'` styles AND the "View Colors" panel's Name page below — always a live network call (no free signal from the interaction payload, no discord.js-level cache to lean on), so callers throttle it the same way banner is throttled (`RECHECK_WINDOW_MS`, always-fresh on a genuine slash command).
- `blendGradientColors([c1, c2])` averages the 2 colors into one hex for use as a Container's flat `accent_color` (Components V2 has no gradient support). Deliberately a simple average — unlike the flat-average approach REJECTED for avatar/banner pixel sampling (see the extraction algorithm's own revision history above), these are exactly 2 deliberate user-picked anchor colors, not thousands of noisy image pixels, so a plain average is the right call here, not the same footgun.
- Falls back to Avatar Color if the user hasn't set one up (same "fall back to the next most personalized style" pattern banner-with-no-banner already uses) — a Nitro name style is a real, common "not set up" case, not a rare edge case.
- **One-time notice, not repeated on every render**: `handlers/settings.js`'s `set_accent_style` handler fires a short ephemeral Components V2 follow-up (`#FF73FA`, Discord Nitro's own brand pink) only when the user actively PICKS `'displayName'` and doesn't have one set up — explains it's a Nitro feature, that Avatar Color is being used meanwhile, and that they can switch anytime. Sent via a raw `POST Routes.webhook(applicationId, token)` call (the follow-up equivalent of `sendV2Payload`'s `PATCH .../@original`) since discord.js's high-level `interaction.followUp({components})` doesn't reliably serialize raw V2 JSON either.
- `/settings`' hex display shows BOTH real gradient stops (`#6D9AFB → #5CCFBA`), not just the blended value — more informative since these are literally the user's own chosen colors, not an approximation.

### 'dynamicProfile' style — randomly picks between every real color source (2026-07-13)
The one style that's genuinely randomized rather than deterministic: on each real NEW slash-command launch, randomly picks between every color source the user actually has (avatar always; banner/displayName/decoration/nameplate only if set), then holds that pick steady across any button/select re-render of that specific message.
- **The hard design problem**: keeping the same random pick stable across button re-renders of one message, without threading a seed through every pagination/toggle button's custom_id across 5+ command files. Solved via `interaction.message.id` — free on every button/select interaction (no fetch needed), used directly as the cache key (`dynamicColorCache`, TTL 24h, mirrors `manageUndoStore`'s short-lived-token pattern). The INITIAL command launch is the only tricky case (no message exists yet at the point accent color must be resolved, before the first payload is sent) — solved by paying ONE extra `interaction.fetchReply()` call (fetches the placeholder message `deferReply()` already created) to learn the real message id right after picking, but only once per genuine command launch under this specific opt-in style, never on the per-click hot path the latency fix above protects. A cache miss on a re-render (TTL expired, or the bot restarted since launch — this cache is in-memory only) gracefully re-rolls a fresh pick rather than erroring.
- Decoration/nameplate colors go through the exact same extraction + still-frame pipeline the "View Colors" panel uses (see below) — an extraction failure EXCLUDES that source from the random pool entirely rather than substituting the command's generic preset color (which would be a silent, misleading "profile color" that isn't real).
- Routed around `resolveAccentColor()` entirely (`resolveDynamicProfileColor(interaction, prefs, presetHex)`) since it fundamentally needs `interaction` itself, not just a pre-resolved `userFetch` — flows automatically to every command already using the shared `getAccentColorForCommand()` hook, no per-command changes needed.

### Clarifications worth remembering
- **Loadout/DMZ commands (`/dmz`, `/all`, `/<category>`) are and remain COMPLETELY unaffected by any accent-color-style customization** — always use their own hardcoded per-weapon-category palette (`getMpCategoryAccent()` in `utils/loadoutRender.js`), never touch `accentColorStyle` at all.
- **`/timestamp` DOES already support every accent style** (avatar/banner/displayName/ dynamicProfile) via the shared `getAccentColorForCommand()` — but ONLY once the user has personally saved a `/timestamp` default style other than "All Formats" (`UserPreference.timestampStyle`). The default "All Formats" overview always stays timestamp's own fixed teal preset regardless of accent style preference — Harkirat's own earlier explicit design call, not something left unwired.
- ⚠️ **PER-SERVER PROFILE COLORS SHIPPED 2026-08-09 13:25 EDT (v3 line) — this bullet used to say the exact opposite and every word of it is now superseded.** It read *"every read uses the GLOBAL profile, never a per-server override… deferred to v4… don't try to solve this under the current user-installed-only architecture."* Its load-bearing premise — that `interaction.member` "is only reliably populated when invoked inside a guild the bot can resolve membership for" — **was measured false.** Discord sends the invoker's full server profile in the interaction payload of **every** guild, including guilds the bot has never joined. The deferral rested on a limitation that did not exist and was never tested.
- **`interaction.member` arrives in THREE shapes, and the difference is not cosmetic** (`BaseInteraction.js:69` — `this.guild?.members._add(data.member) ?? data.member`): a real **`GuildMember`** in a guild the bot has joined · the **raw snake_case API payload with no methods** in a guild it has not (calling `displayAvatarURL()` there throws) · **`null`** in DMs. `utils/guildProfile.js`'s `readGuildProfile(interaction)` is the single normalizer for all three; it builds CDN URLs from raw hashes via `client.rest.cdn.guildMemberAvatar/guildMemberBanner`, which works regardless of shape. **Never branch on the shape at a call site** — that is what this module exists to absorb.
- **All five sources are per-server** (measured live 2026-08-09 13:19 EDT across three real guilds with different overrides in each): avatar · banner · decoration · **nameplate** · **display-name styles**. ⚠️ **A `null` on any of them means "no override in this guild", NOT "unsupported"** — reading one `null` sample as absence-of-support is exactly how nameplates and name styles were each wrongly written off once during this build, both corrected only because Harkirat set a real value and asked for a re-test. **Re-test with the value actually set before concluding a source cannot be read.**
- **The one asymmetry is backwards from intuition.** Four sources are free from the payload everywhere. **`display_name_styles` is dropped by discord.js's `GuildMember._patch`**, so it is readable for free in guilds the bot has **not** joined and needs a REST `GET /guilds/{id}/members/{user}` in guilds it **has** — the same call that returns **404 Unknown Guild** in the other case. The two paths are complementary and both are handled by `resolveGuildNameColors`; its throttle cache is keyed **`${userId}:${guildId}`** because it is the one genuinely guild-dependent fetch. **`bannerRecheckCache`/`profileExtrasRecheckCache` stay keyed by userId alone on purpose** — they hold GLOBAL data that does not vary by guild, and adding a guild id there would fragment a correct cache into one entry per server.
- **Guild colors cache under their own `guild*ColorHex`/`guild*ColorSource` field pairs, keyed on the image hash and deliberately NOT on the guild id.** Guild-keying looks obviously right and is wrong: measured 2026-08-09 13:10 EDT, the same server avatar reused across two different guilds returns the **identical hash**, so hash-keying makes the second guild a free cache **hit** while guild-keying would recompute the same pixels under a new key. A different server profile necessarily means a different hash, so correctness never depends on the guild id. Separate field pairs (rather than one shared pair) exist so moving between a server and a DM does not have each context evict the other's cached color. **No invalidation migration was needed** — new fields start empty and fill naturally.
- **Two real bugs were found and fixed in the same change, neither of them guild-specific.** (1) `fetchProfileExtras` required `colors.length >= 2` and so classified a **solid** (single-color) name style as "not set up", silently falling back to avatar — `normalizeNameStyleColors` now pairs a solid with itself so the blend returns that exact color. A global solid style had been mishandled this way the whole time. (2) `getCachedColor`'s `userFetch.avatar || 'default'` hash is safe **only** because `userFetch` is always a `User`; passing a `GuildMember` would collide every override-less member into one `'default'` bucket that stops invalidating when their global avatar changes. Guild sources are routed through `guildProfile` specifically so a `GuildMember` never reaches that line.
- ⚠️ **`readGuildProfile` returns `null` when the clicking member is not the panel's owner**, because `utils/interactionContext.js`'s `resolvePanelActor` admin-override builds a synthetic interaction with `.user` swapped but `.member` left as the admin's — reading the guild profile there would paint Harkirat's own server avatar onto someone else's panel with no error. If you add another path that swaps `.user`, that guard is what protects it.

### The color extraction algorithm — went through a full redesign, not a tuning pass
**V1 (2026-07-13, REJECTED same week)**: an Android Palette-style 6-swatch model (Vibrant/ Light Vibrant/Dark Vibrant/Muted/Light Muted/Dark Muted, later +Dominant/+Average). Rejected after Harkirat compared it directly against real palette-generator tools (Jukebox, Coolors) run on his own avatar — their results were genuinely diverse real colors sampled from visually distinct regions of the image, while the synthetic category system read as "mostly useless." **Before rebuilding, the naive alternative was tested and found WORSE**: ranking real sampled pixels by raw population and taking the top N produced 4 near-identical off-whites on Harkirat's own avatar (`#F5F4F3(34.5%) #EBEBE9(26.1%) #EEEEF1(2.7%) #F3F1ED(2.1%)`) — the exact "background dominates" failure mode `getDominantColor()`'s own "vivid" algorithm was built to avoid in the first place.

**V2 (2026-07-13, ⚠️ SUPERSEDED by V3 below — kept as the record of what V3 replaced and why)**: real K-MEANS clustering in RGB space, the actual technique those reference tools visibly use (confirmed: Coolors' own UI shows pin markers landing on chromatically distinct regions — background, hair, eye, skin, shirt — exactly k-means' expected behavior, since a large uniform region becomes ONE cluster regardless of pixel count while smaller distinct features still get their own). `getColorPalette(imageUrl, count)` returns a plain array of `{hex, percent}` sorted by prevalence, NOT a named-fields object — there's no more fixed category set to key off of.
- **Determinism is required, not optional**, specifically because of the "Refresh Colors" button's honest change-detection (below) — it needs the SAME image to always produce the SAME result, or even an unchanged avatar would look "different" on every refresh. Textbook k-means uses randomized init (k-means++); fixed by seeding centroids DETERMINISTICALLY instead (sort sampled pixels by hue, pick K evenly-spaced ones as starting centroids — same spread-out spirit as k-means++, zero randomness). Verified live: ran extraction twice against the same real avatar/banner URLs, byte-identical both times.
- **A post-clustering merge step** folds any 2 final clusters within 30 RGB-distance back into one (population-weighted average) — confirmed empirically that plain k-means could still occasionally split a subtly-varied region (a background with soft lighting gradient) into 2 near-duplicate clusters depending on where the deterministic seeds landed.
- **REAL BUG found and fixed, not just a caching gotcha**: requesting 8 colors for avatar only returned 5 even with the merge step in place — clustering at exactly K=8 then merging could eat INTO the requested count with no way to recover lost slots, even though the image likely had other genuinely distinct regions available to fill them from. Fixed by over-clustering first (K = 1.5× requested) before merging, then slicing to the top `count` post-merge — gives the merge step room to fold away real near-duplicates while still hitting the requested count from other distinct regions. Verified: avatar went from 5/8 to a full 8/8, determinism re-confirmed unaffected.

### 🔦 The low-colour restrict, rebuilt: it asks about the PIXEL TAIL, and it picks survivors by LIGHTNESS (2026-08-12 15:07 EDT)
Harkirat's original ask is unchanged — a genuinely near-colourless image should show 4 swatches instead of 8. What changed is that **both halves of it were wrong**, and fixing only the half on the tracker would have left the other one shipping.

**The gate was answering the wrong question with a borrowed constant.** It asked "does any extracted centroid reach `CHROMA_FLOOR` (0.04)?" — but `CHROMA_FLOOR` exists to decide *whether a pixel is worth putting in the accent pool*, where 0.04 is a sensible bar for a small punchy feature. "Does this image have colour at all?" is a different question and 0.04 is far too high a bar for it: every sepia photograph, brown avatar and olive banner sits under it while being unmistakably brown to anyone looking at it. **Measured on the 246-image corpus: the old gate fired on 9 images and 4 of them were tinted, not colourless** — a sepia portrait topping out at chroma 0.027, two brown avatars at 0.033 and 0.037, a dark olive at 0.017. Harkirat's own server avatar was one: the structure pool found a real black and two dark browns correctly, and the restrict discarded all three for having no saturation, **which is not the same fact as having no depth**.
- **`LOW_COLOUR_CHROMA` (0.01) is now its own constant, read off `tailChroma`** — the chroma of the image's most-chromatic 3% of pixels, hoisted out of `tailCut` so the two floors sit side by side and the difference is visible.
- 🚫 **The old note said "judged on the EXTRACTED colours, not on raw pixel statistics — that distinction is load-bearing", and this reverses it.** The reasoning was right about *aggregate* chroma: a black cat's mean chroma is low while its red eyes are real. But a **percentile** is a raw pixel statistic that does not have that failure — it is the very statistic the accent pool already uses to *find* those eyes. The old rule rejected a whole family for a flaw belonging to one member of it. The black-cat case is still protected, by the same arithmetic that always protected it.
- ⚠️ **This is also what removes the boundary flip, BY CONSTRUCTION rather than by moving a threshold.** `tailChroma` is computed from the sampled pixels before a single centroid exists, so it cannot depend on `count`; the old test read the extracted candidates, which do change with the requested count, so one image could be colourful at target 6 and colourless at target 8. **Measured at both targets: the old gate disagreed with itself on 3 images, the new one on 0.** The separate cherry-blossom hysteresis item is closed by this, not deferred — there is no longer a continuous quantity being hard-cut at a count-dependent point.
- **0.01 is not fitted to the corpus.** It is where a colour is, by this module's own merge rule, the same colour as plain grey: `MERGE_DELTA_E` calls two entries identical below 0.07 of OKLab distance, so a tail within 0.01 of the neutral axis is nowhere near a distinguishable hue. The corpus then confirms it isn't delicate — achromatic images measure 0 to 0.0031, the least colourful genuinely-tinted one measures 0.0213, a **7× empty band** around the value.

**The truncation was the other half, and fixing the gate alone would have left it.** When the restrict fires, the survivors are now chosen by **lightness coverage**, not by salience. On a colourless image the salience blend collapses to prevalence (every chroma term is ~0), so a plain `slice` returns the four largest regions — which on a greyscale ramp are four neighbouring mid-greys. **Measured before the fix: a black-and-white avatar kept four near-whites and discarded a real black covering 11% of the picture; another dropped both `#000000` (11%) and `#111111` (17%) to keep two near-identical light greys.** Lightness is the only axis carrying information on such an image, so spanning it is the only defensible way to spend four slots.
- `spanLightness` is farthest-first on L — the same deterministic Gonzalez traversal `seedFarthestFirst` already uses, in one dimension. Index 0 is held fixed (it is a contract), and the winners are returned in **input order**, so this changes which entries survive and never the order they arrive in. Determinism is preserved, which the Refresh Colors button's "did anything actually change?" comparison depends on.
- ⚠️ **It selects from `ordered.slice(0, count)`, NEVER from all of `ordered`, and that bound is load-bearing.** Clustering over-asks by 50%, so `ordered` normally runs longer than `count` and everything past it is surplus the extractor already ranked out. Handed the unbounded list, the first draft picked `#1C1C1C` for a black-and-white avatar — **a colour that image's own unrestricted palette would never show.** A soft restrict must return a SUBSET; showing fewer colours cannot mean showing different ones. It was caught by diffing restricted against unrestricted output, not by reading the code, and it is invisible from the outside — the palette simply contains a plausible extra grey.
- 📊 **Net effect over the corpus at target 8:** 11 of 246 images changed, restricted images went 18 → 14, total swatches 1,837 → 1,850. Harkirat's avatar goes 4 → 8 and regains `#3F342E`, `#28241D` and `#040303`. Nothing outside the fired set moved.
- 🧪 **`scripts/paletteShape.test.js` (in `npm test`)** pins the gate in both directions, the count-independence, the `count` bound and the selection rule. **Every failure mode here is silent** — a palette that is merely short looks exactly like a palette of a simple image — which is why the original bug survived until Harkirat noticed black missing from his own avatar by eye. ⚠️ **The sepia fixture's tint is CALIBRATED, not eyeballed**: its top pixels measure 0.037, inside the 0.0213–0.0395 band the real misjudged images occupy. A stronger tint was tried first and was useless — it cleared 0.04 outright, so the case passed under the old gate too and proved nothing.

### ⚡ The montage is passed as a DECODED IMAGE, and its tiles are COPIED not composited (2026-08-11 15:20 EDT)
Palette extraction inside the WebP render was measured at ~350ms, of which the colour maths was **37ms**. The rest was plumbing, and three pieces of it are now gone. Full before/after harness: `local/colors-investigation/pipeline-parity.js`, which runs the shipped `poolFramesIntoMontage` against three real Discord assets and compares palettes against independent reference implementations of each variant.
- ⚠️ **`poolFramesIntoMontage` returns a Jimp IMAGE, not a PNG buffer, and `getColorPalette` accepts one.** It used to encode the sheet so the very next call could `Jimp.read` it back; nothing ever stored or displayed that PNG. Measured **28ms / 56ms / 84ms** saved on three real assets, palettes byte-identical. **Do not "restore" the buffer return for tidiness** — if a caller ever needs bytes it can ask for them, but no caller does.
- ⚠️ **Tiles are blitted with `Buffer.copy`, and that is the ACCURATE option as well as the 100× faster one.** Compositing "source over a fully TRANSPARENT destination" is mathematically the source itself, so this step never had anything to blend; Jimp's `composite()` runs the over-operator anyway and its rounding returns source **±1** on every partial-alpha pixel (13,134 altered bytes on twilight, 67,175 on a real decoration — enough to move a swatch, `#117AF1` → `#127BF2`, where **the copy's value is the correct one**). 83–98ms → 0.5ms. A uniform-tile-size guard falls back to `composite()`; every frame of one animation is the same size, so it is insurance.
- 💾 **`extractAlphaFrames` has an opt-in `asPaths` mode — the frames stay where ffmpeg wrote them.** The decoration render and its heal path use it; the nameplate render does NOT, because it composites a bed onto every frame and genuinely needs the pixels. Removes 60 writes and 51 reads on a 60-frame decoration (the montage samples 9; the rest were read to be discarded). ⚠️ **The caller then OWNS the temp dir — `cleanup()` must run in a `finally`**, which is why it is opt-in rather than the default. ⚠️ **Never fold `asPaths` into a cache's `FRAME_OPTS`**: it moves no pixel, so keying the palette cache on it would re-derive everything for identical colours. Spread it in at the `extractAlphaFrames` call only.
- **`readImageSize()` (`animatedMediaPipeline.js`) reads PNG width/height from the IHDR header** instead of decoding a frame, for the one caller that only needs dimensions (`decorationWebpCache.js`'s resize branch). Falls back to a real decode on a non-PNG, so it can never be why a render fails.
- ⚠️ **The ~350ms was NEVER a regression, and the changelog says so on purpose.** v3.7.0 moved extraction *into* the render from `colorPalette.js`, where it paid its own fetch and its own ffmpeg pass — the render's timer started covering work that used to happen out of its sight. Total work went **down**. Don't write it up the other way.
- 🏷️ **A stored palette records WHICH ALGORITHM produced it, as a hash DERIVED FROM THE CODE — never a version number anyone maintains** (`PALETTE_ALGO_VERSION` in `colorExtract.js`, built by `utils/algoFingerprint.js`). ⚠️ **No hash value is written down here on purpose** — it changes by design, so a copy in prose would rot and then misinform. Read the current one with `node -p "require('./utils/colorExtract').PALETTE_ALGO_VERSION"`, and note that is the shared BASE: each cache folds its own `FRAME_OPTS` in, so the value actually stored differs per media type. Written to Cloudinary `context` as `palette_version`; **read back as a gate** — `readPaletteContext()` returns `null` for anything tagged otherwise, and `null` is already what both caches route through `healPalette`, so a stale entry **re-derives itself in place on next view**. Needed because the cache keys on the ASSET HASH, which never changes when an extractor does — the same trap `[[feedback_cache_invalidation_on_algorithm_change]]` records for the per-user caches.
  - 🚫 **DO NOT replace this with a hand-written release tag.** That was the first design and Harkirat rejected it 2026-08-11 15:44 EDT: *"there's a unique versioning for the actual algorithm."* It fails in **both** directions, silently — it only moves when someone remembers (so a real change ships under a stale tag with every cached value quietly wrong), and naming it after a release invites bumping it every release (re-deriving identical output for nothing). **Shipping any new version does NOT change this hash and forces no re-derivation.**
  - ⚠️ **EVERYTHING UPSTREAM OF THE EXTRACTOR IS PART OF THE HASH — a palette depends on the PIXELS as much as on the clustering.** `poolFramesIntoMontage` decides which frames are pooled and how they land on the sheet; `extractAlphaFrames` decides which frames exist at all. Both are in `MONTAGE_FINGERPRINT`, exported by `animatedMediaPipeline.js` and required by `colorExtract` (no cycle — the pipeline requires nothing back). Hashing `colorExtract` alone would have missed v3.8.0-pre's own tile-copy fix, which moved a swatch while touching nothing in that file.
  - ⚠️ **The per-cache `FRAME_OPTS` are folded in AT THE CALL SITE, and that asymmetry is deliberate.** fps and the decoder flags live in the two cache modules and differ per media type (`-c:v libvpx-vp9` is what makes a nameplate's alpha survive; `-f apng` is what stops ffmpeg reading a 60-frame decoration as one still), and importing them into `colorExtract` would close a cycle. So each cache passes `FRAME_OPTS` as the `extra` argument to **both** `paletteContextFields` and `readPaletteContext`. ⚠️ **Give both halves the same extras or a freshly-written palette reads back as stale forever** — symmetry is enforced by keeping the write and the read in one module, and pinned by a test. Nameplates and decorations therefore carry **different** keys; that is correct, not drift.
  - ⚠️ **Comments and whitespace are stripped before hashing**, deliberately: these files are comment-dense and comments get edited constantly, so hashing raw source would invalidate every cached palette on every clarified sentence. It errs toward OVER-invalidating (a renamed local moves it) because the failure modes are not symmetric — a false invalidation costs one metadata re-derive; a missed one leaves a wrong value cached forever behind a marker swearing it is current.
  - 🧪 **`scripts/paletteAlgoVersion.test.js` (13 cases, in `npm test`) pins BOTH directions** — a comment rewrite and a reindent must not move the hash, a changed body/constant/montage must. Plus the round trip: another algorithm's tag, no tag, and a malformed palette all read as absent, and an empty palette writes no marker rather than a marker with nothing under it.
  - 🚫 **There is no purge script and none is wanted.** Deleting the Cloudinary resource takes the render and its `discord_cdn_url` with it; the gate re-derives the metadata alone. And never an unscoped `updateMany({})` on the per-user side.
  - ✅ **Verified live 2026-08-11 16:02 EDT on the real dev cache:** both PROD folders hold **zero** resources (every render so far is dev-scoped), so the reset had nothing user-facing at stake. The decoration whose swatch the rounding had moved came back `#117AF1` → `#127BF2`; each subsequent key change re-invalidated the entries and they re-derived again, and **`discord_cdn_url` survived every one of those patches** — the thing that breaks if `context` is written in two calls instead of one. A fourth entry was left **untouched** by a harness URL typo, which is the designed degradation: a heal that cannot complete returns the cached object rather than writing a partial context.
  - ⚠️ Both halves live in `paletteContextFields()` / `readPaletteContext()` so the four write sites and two read sites cannot drift on the key name — the same reasoning that moved `PALETTE_COUNTS` into this module.
- 🚫 **Two faster options were measured and NOT taken, because they cost real palette quality rather than rounding error:** skipping the 256px tile resize (333 → 245ms, `#3DE7E9` → `#39E8E8`) and pooling 4 frames instead of 9 (333 → 130ms). Both change *what the extractor sees*; the two changes above change only what it wastes. **Don't conflate the categories** — the blit was takeable precisely because it removed error instead of removing data.

### 🔧 Two "latent traps" that turned out to be FIXABLE, and the lesson in why they were nearly filed instead (2026-08-11 17:35 EDT)
These were first written up here as things *no automated check could see*, with the reasoning that documenting them was the only available mechanism. **Harkirat rejected that outright** — *"why was that even sidelined or not properly documented OR NOT FIXED ALTOGETHER?"* — and he was right. The reasoning confused two different claims: they could not be **observed** by an existing check, but each could be **made checkable** by changing the code so the invariant is *enforced* rather than *assumed*. That is the exact failure `[[feedback_not_checkable_is_usually_unexamined]]` describes, and "documented" is not "closed" — a note goes stale, a reader skims it, and the failure it warned about ships anyway. **Both are now enforced in code and pinned by `scripts/animatedMediaPipeline.test.js`.** Kept here as the record of the reasoning error, not as an open warning.
1. ✅ **FIXED — the frames directory is shared with the encoder's output, so its file filter is now EXACT.** `encodeWebpFromFrames` writes `out.webp` in beside `frame_0001.png…` (that is what removes the second temp dir), while `extractAlphaFrames` reads frames back out of the same directory. It used to select them with `startsWith('frame_')`, which was safe only by *accident* of the output being named `out.webp`. Now a single `FRAME_FILE_RE = /^frame_\d+\.png$/` both describes ffmpeg's `frame_%04d.png` output pattern and reads it back, so the two cannot disagree, and the test asserts a hostile `frame_out.webp` is rejected.
2. ✅ **FIXED — a non-uniform frame set now THROWS instead of falling back to `composite()`.** The fallback looked like the safe choice and was the opposite: `composite()` is the path that re-adds the ±1 rounding the row-copy exists to remove, so it would have produced **different colours from the same code** — and `PALETTE_ALGO_VERSION` cannot tell two runtime branches apart, so the cache would have stamped both alike. It cannot fire for a real caller (every frame of one animation shares its stream's dimensions); if it ever does, the caller assembled frames from more than one source, which this function does not support. Both callers wrap extraction in a try/catch that degrades to no palette, so failing loud costs a palette, never a render.

### ⚠️ One trap that genuinely stays documented, because it cannot be enforced from inside
3. 🔤 **The fingerprint's comment-stripper is a REGEX, not a JS parser.** `utils/algoFingerprint.js` removes `//…` to end-of-line and `/*…*/` before hashing. A `//` or `/*` **inside a string or regex literal** in any fingerprinted function would take real code with it. Checked against today's actual inputs — the only slashes are in `'image/png'` and ffmpeg flags (`-c:v`, `-f`, `-vf`) — so it is safe now. The risk if it ever changes is **collision, not corruption**: hashing stays deterministic, but two genuinely different implementations could normalise to the same text, and that failure direction is the expensive one (a missed invalidation, not a spurious one). **Adding a URL, a regex literal, or a comment-like string to a fingerprinted function is the trigger.**
- 🏷️ **Nameplate public ids are `<design>-<palette>`, not the full asset path** (shortened 2026-08-11 17:34 EDT — Harkirat asked why `dev_nameplate_webp/nameplates-nameplates-twilight-cobalt` was so long, and the honest answer was that nothing had questioned it; Discord serves every nameplate under `nameplates/nameplates/<design>/`, so two thirds of that id was a constant). ⚠️ **Only the exact three-segment `nameplates/nameplates/<design>` shape is shortened** — anything else keeps the full slug, because a tail segment is only unique when its parent path is known-constant. ⚠️ **The public id IS the cache key, so changing it orphans every render stored under the old name.** It was safe precisely then: both prod folders held zero resources and the dev entries were purged and re-rendered in the same pass. Do not repeat it casually once real renders exist.
- 💸 **And the standing cost, which is not a trap but is easy to forget:** `extractAlphaFrames` and `poolFramesIntoMontage` are inputs to the palette key, so **any edit in `animatedMediaPipeline.js` re-derives every cached palette** — even a provably byte-identical refactor. Confirmed in practice twice on 2026-08-11. It is metadata-only, automatic, and costs one ffmpeg pass per design on next view; it is not a reason to avoid editing the file, only something to expect rather than be surprised by.

### 🏷️ Swatch LABELS are a VOCABULARY, not a rule→label map — rewritten 2026-08-12 14:07 EDT
The caption under each swatch says what the colour DOES in the picture, not where it ranks. This is the **fourth** attempt and each rejection taught something the next one had to keep; the rules were right by attempt three and only the *words* were wrong.

**The register: self-contained NOUN phrases.** Harkirat, 2026-08-11 22:17 EDT, on *cools it down · cuts against it · warms it up · sets the tone · fills the space · backs it up · adds depth · opens it up* — **"what is 'IT'???"** Every one is a verb phrase whose object is an antecedent the caption never supplies, which is the same defect as the earlier "Lighter Version" (than what?) / "Same Family" (as what?) rejection wearing a verb instead of an adjective. **"Catches the Eye" survives only because "the eye" is the reader's own, not a swatch.**
> 📌 **THE TEST FOR ANY NEW LABEL: read it alone, with no other swatch visible. If it makes you ask "than what?" or "of what?", it is the rejected pattern again, however it is worded.** A comparative adjective fails it too — `Deeper Shade`/`Lighter Tint` were rejected on sight for exactly that.
- ⚠️ **This section previously said the opposite** — *"the ones that worked were all **verb phrases** that stand alone"* — and that sentence is what the 2026-08-12 rework had to undo. Kept visible here because a future session reading a stale claim would rebuild the rejected set.
- ⚠️ **Words from the SUPERSEDED set are NOT banned, and assuming they were cost a whole round.** Harkirat marked `Light Highlight`, `Soft Tint` and `Muted Accent` neutral and **liked `Vibrant Accent`** — so what was rejected in that set was **rank-and-comparison as a system**, never the vocabulary. A first pass at this rework binned four candidates purely for resembling old labels; that was wrong.
- 🚫 **"A category word + `Color` is not a label."** `Base Color` was rejected on sight as lazy and generic (2026-08-12 00:50 EDT), the same objection that killed `Majority Color` and `Secondary Color`. The dominant swatch is **`First Impression`** — what dominating an image actually does to a viewer.
- 📐 **A RULE PICKS A VARIANT, and that is the architecture.** Harkirat kept answering the naming menus with *two* words and when each applies — on soft vs muted: *"soft implies lighter, gentle, whites, greys, baby pink, powder blue… muted implies matte, sophisticated, darker, slate blue, dusty rose. While yes they're kind of the same thing, they also have situations where 1 is better than the other."* So a rule answers **which role** the swatch plays and the variant answers **what the swatch is like**, chosen from its own chroma/lightness: `Prominent`/`Backdrop` · `Warm Accent`/`Warm Trace` · `Wild Card`/`Outlier` · `Undertone`/`Deep Tone` · `Loud Accent`/`Vibrant Accent` · `Soft Accent`/`Muted Accent` · `Harmonic`/`Neighboring Shade`/`Muted Harmony`/`Neutral Shade` · `Vivid Echo`/`Echo`/`Quiet Echo` · `Brightest Point`/`Palest Tone`/`Lightest`. ⚠️ **A variant must answer to a measurable property or it is noise** — a full "Lightest/Palest/Brightest × Note/Shade/Tone/Point" matrix was floated and cut to the three adjectives, because twelve cells need twelve distinguishable states and there are three.
- 🤝 **`Synergetic Hue`/`Synergetic Shade` is a genuine relationship, not decoration.** At 150–210° of hue with real chroma on both sides the pair is COMPLEMENTARY — the one relationship where two hues reinforce each other — so calling it `Outlier` frames a deliberate scheme as a mistake. ⚠️ **It must outrank the temperature rules or it never speaks**: a complement is almost always the opposite temperature too, and while `Cool Accent` sat first this tier fired **once in 889 swatches**. `Cool Accent` was not wrong there, only vaguer, and **the more specific true thing wins**.
- 🚫 **RANK IS NOT A LABEL RULE, and must not come back.** "Most Common" means *it is first in the list* and "Second Most Common" means *it is second* — the reader is looking at the order, so those captions carried **zero** information. They were not fixable by renaming.
- ⚠️ **The fallback pool is NOT a rotating list.** A rotation hands out whichever word is next, so a punchy magenta could draw `Quiet Hint` purely because the counter sat at 0 — the one place in the function where the caption would be unrelated to the swatch. It is ordered by what the swatch IS (`Hint of Color` punchy · `Trace of Color` · `Stray Shade` dark · `Stray Color` · `Quiet Hint` · `Side Note`), per Harkirat's own distinctions: *"Quiet Hint if it's a softer color or very minimal and Hint of Color if it's more punchy"*, and Stray Shade vs Stray Color *"because shade and color kind of are different things"*.
- ⚠️ **`percent` IS NOT A SHARE OF THE IMAGE for anything restored from cache**, so every area rule reads it through a normaliser. See the pool double-count fix in `docs/archive/resolved-list.md` (closed 2026-08-12 13:26 EDT): a fresh palette now sums to 100, but a palette cached before that fix does not, and the label layer is what protects the thresholds from it.
- 📐 **The accent pool reaches this layer on purpose.** `getColorPalette` returns `origin`, and an `accent` entry is by construction a small high-chroma FEATURE (the cat's red eyes, the gold sparkle). It is the only fact in the label function that statistics cannot recover, and it drives **Catches the Eye** / **Pop of Color**. ⚠️ `origin` is **absent** on palettes restored from a Cloudinary entry written before the wire format gained its `:a` flag — missing is treated as `structure`, so no rule may REQUIRE it.
- ⚠️ **Pool membership alone is NOT enough** — the accent pool is the most chromatic tail *of its own image*, so on a sepia photo it returns beige. A first build labelled `Tan → Catches the Eye`. Both accent rules also require the colour to beat the palette's median chroma **and** clear an absolute floor.
- 🐛 **COLOURFULNESS IS JUDGED IN CHROMA, NEVER HSL SATURATION — this was a real pre-existing bug, found 2026-08-11 14:00 EDT.** HSL's `s` denominator collapses at extreme lightness: **`#FDFEFE` (white to any eye) reports s = 0.333 and `#020311` (black) reports 0.789.** Every saturation threshold in this function had therefore been meaningless for near-whites and near-blacks — two of the commonest swatches there are. All 13 judgements now use `chromaOfHex` from `colorExtract.js`. ⚠️ **Chroma's range is ~0–0.37, not 0–1** — an `s` threshold pasted in without rescaling is wrong by roughly 3×.
- **The captions, grouped by what they answer.** *What it is*: First Impression · Nameplate Background · Catches the Eye · Pop of Color · Prominent · Backdrop · Edge Detail. *Palette extremes*: Deepest Shadow · Brightest Point · Palest Tone · Lightest · Quiet Neutral. *How it sits against the dominant colour*: Synergetic Hue · Synergetic Shade · Warm Accent · Warm Trace · Cool Accent · Cool Trace · Wild Card · Outlier · Undertone · Deep Tone · Highlight · Loud Accent · Vibrant Accent · Soft Accent · Muted Accent · Harmonic · Neighboring Shade · Muted Harmony · Neutral Shade · Vivid Echo · Echo · Quiet Echo. *Safety net*: Hint of Color · Trace of Color · Stray Color · Stray Shade · Quiet Hint · Side Note. ⚠️ **No count is written here on purpose** — it moved four times in one morning and a number in prose rots into misinformation. `node local/colors-investigation/label-corpus.mjs --audit` prints the live one. The non-numbered fallback stays a safety net — a numbered "Accent Color N" was the very first version and was rejected outright.
- 🧪 **THE CORPUS IS A FALSIFIER, NEVER A TUNER — `local/colors-investigation/label-corpus.mjs`.** 246 real avatars and banners, 1,837 swatches, extracted once into JSON so a wording iteration costs ~0.2s. It exists to catch captions that are **false**, never to decide which labels deserve to exist by frequency. Harkirat, 2026-08-12 11:27 EDT: *"it's meant to define an unlimited/undefined number of inputs… we need those rules/vocabularies which fit the real world edge cases and not just refined for our limited corpus."* A label firing once is fine; a label that **cannot** fire because another rule always claims its swatch first is a defect — that distinction is how both `Loud Accent` and `Synergetic` were saved.
  - **Every defect it has caught, each invisible at 20 images:** an accent caption on a swatch covering **46%** of the picture (`Pop of Color` had no size ceiling at all — pool membership says a colour is chromatic, never that it is small) · `Quiet Echo` on a neon orange-red at chroma 0.19 · `Harmonic` on greys with no hue to harmonise with · `Stray Color` on near-black swatches · a hue claim on two greys 130° apart · and the extractor's own percentages summing to 155%.
  - ⚠️ **The harness must sample animations the way production does.** Its first version read GIF **frame 0** while production pools the whole cycle through `extractFrameMontage`, so nine of twenty palettes were not palettes any user could see. It now calls that same function — only the file read is stubbed, since Node's `fetch` has no `file:` support. ⚠️ Use `pathToFileURL`, never a `file://` template: the corpus contains `#kittens.gif` and a raw `#` parses as a URL **fragment**, which silently resolved to the parent directory and skipped the image.
  - ⚠️ **There is no avatar/banner split, and re-adding one would be wrong.** `assignDynamicLabels` branches on `nameplate` alone; avatar and banner take identical paths and identical counts. Classifying by aspect ratio was **refuted by measurement** (corpus avatars span 0.51–1.46, banners 1.20–3.00) and by Harkirat's simpler objection: a tall image could be cropped square for an avatar or rotated for a banner. A subfolder still sets the kind when it names one that MATTERS (`nameplate/`, `decoration/`).
  - 🧾 **Paths exercised beyond the corpus, all verified 2026-08-12, in the same session as the extractor fix:** a nameplate's prepended bed (`percent: 0` at index 0) passes through every area rule cleanly; **`origin` stripped from all 246 palettes throws zero times** — 1,512 captions identical, 325 degrading to another true caption — which finally *tests* the documented "no rule may REQUIRE `origin`" invariant rather than asserting it; and empty / single-entry / duplicate-hex / all-zero-percent palettes return without a crash or a `null` caption.
- ⚠️ **Saturation comparisons need a COLOURED reference.** When the dominant colour is achromatic, every other swatch is trivially "more colourful", which once labelled a pale pink on a white avatar the boldest thing in the picture — true by arithmetic, absurd to read. Those rules are skipped below a dominant-chroma floor; the colourless-ground case is answered instead by **Catches the Eye** at the top of the function (the vivid swatch IS what your eye goes to) and by **Vibrant Accent**.
- ⚠️ **A HUE claim needs a colour to be about, exactly as a saturation claim does.** Hue is meaningless at near-zero chroma — two greys a rounding step apart can sit 130° away from each other — so the temperature and odd-hue rules carry their own floor. Without it, `#BABCB0` was captioned as clashing against a `#9CA6AC` dominant: two greys, one accused of fighting the other. The corpus split was unambiguous (every near-neutral claimant at chroma 0.016–0.033, every genuine one at 0.054+), which is where the floor sits.

2. Its own top-level sibling row OUTSIDE the container (same convention the global nav row/ Share Publicly button already use — a new top-level row, never packed into the container), style 1 (blurple) + the eyedropper emoji, matching "View Colors" itself.

- 🔄 **It also picks up OTHER sources whose image genuinely changed** (`refreshStale`, added 2026-08-11 18:47 EDT to Harkirat's design): besides force-re-extracting the source on screen, it recomputes any other equipped source whose stored hash no longer matches the live one, and leaves the untouched ones alone. ### Known-not-a-bug: a single click can show DIFFERENT before/after data than expected, and it isn't ours
**Incident, 2026-08-11 22:34 EDT — logged for reference in case it recurs.** Same live session as the bug above: Harkirat reported that View Colors, on FIRST open (which force-refreshes per above), still showed his OLD server avatar and OLD swatches — only updating to the new ones after he *then* clicked Refresh Colors, even though both calls use the identical forced-extraction path. Traced the entire chain looking for an in-repo caching bug and found none: `getCachedPalette`'s cache-hit shortcut is gated `if (!forceRefresh && ...)` (colorPalette.js:180) so `forceRefresh: true` always skips it and re-extracts+re-saves; the guild avatar data itself comes from `readGuildProfile(interaction)` reading `interaction.member` directly (guildProfile.js:50) — the member payload Discord attaches to *that specific interaction*, not a locally-cached copy. Every step that runs on View Colors' open is wired to force a real re-extraction against current-at-click-time data. **Working theory, unconfirmed and unfixable from our side if true:** Discord's own avatar-change propagation hadn't finished at the exact moment View Colors was first clicked, so the bot's forced fetch correctly got Discord's still-stale answer; by the time Refresh Colors was clicked moments later, Discord had caught up. If this recurs, the diagnostic path is the same: confirm `forceRefresh` reaches `getCachedPalette` (it does, structurally, per above) before suspecting our cache — the interesting question is only ever *what did Discord actually serve at that instant*, which we have no way to inspect after the fact.
- **REAL BUG found and fixed**: the panel correctly said "found new colors" but kept showing the OLD swatch images until switching pages and back. Root cause: `sendV2Payload.js`'s raw multipart `PATCH` never included Discord's `attachments` field in the JSON body when uploading new `files` — Discord's edit-message API needs this field to know whether new attachments should REPLACE or ADD TO a message's existing ones; omitted, Discord could retain the OLD attachments instead of cleanly swapping in the new swatch images, even though text/components updated correctly (that part doesn't depend on `attachments` at all, which is why the confirm message worked while the images silently stayed stale). Fixed: whenever `files` is passed to `sendV2Payload`, also set `body.attachments = []` — confirmed via grep this is safe bot-wide, only the 5 View Colors call sites ever pass `files` at all, and every one of them always fully regenerates its complete attachment set on every render (never expects to "keep" one from a prior render).

### Still-frame extraction for animated sources (`utils/stillFrame.js`)
Avatar decorations are commonly served as **animated PNG (APNG)** — confirmed live against a real equipped decoration, Jimp (this whole color system's underlying image library) cannot decode APNG at all (`Mime type image/apng does not support decoding`). `extractStillFrame (sourceUrl)` downloads the source and pulls exactly ONE still frame via `ffmpeg` (`-vframes 1 -update 1` — the `-update 1` flag avoids a spurious "missing %d sequence pattern" warning ffmpeg otherwise prints; confirmed present on this host but NOT a guaranteed system dependency elsewhere) into a PNG Buffer Jimp reads identically to a URL. Deliberately general-purpose, reusable for any other animated source, not decoration-specific. Wired into BOTH places decoration extraction happens (`colorPalette.js`'s `getCachedPalette` for the View Colors panel, `accentColor.js`'s `getCachedDecorationColor` for the `'dynamicProfile'` pool) — the cache check runs BEFORE the still-frame extraction step so a cache hit never pays for an unnecessary ffmpeg call. Nameplate's `static.png` doesn't need this (already guaranteed static); avatar/banner don't either.

### Post-ship production incident: stale palette cache + bot-wide interaction timeouts (2026-07-13)
Harkirat reported `/colors` still showing 5 old-labeled swatches for avatar right after `219b2e1` deployed, even after re-running it, hitting `/settings`' View Colors button, and clicking Refresh Colors (which itself claimed "still generates the same colors"). Root-caused via `systematic- debugging`, two distinct bugs stacked on top of each other:
1. **Stale cache, never invalidated.** `219b2e1`'s over-clustering fix (avatar 5/8 → 8/8, see the k-means algorithm section above) was never followed by the same one-time cache-clear the earlier "vivid" accent-color rewrite did (`e5359df`) — confirmed directly: Harkirat's live `avatarPalette` in Mongo had exactly 5 entries, already in the new k-means array shape (so not leftover V1 data — a k-means result computed before the over-clustering fix landed, most likely from same-day local dev iteration hitting the same production `MONGODB_URI`). Running the *current* `getColorPalette()` directly against that same avatar URL correctly returned 8. Fixed with a one-time `UserPreference.updateOne({discordId: '1139845545754632283'}, {$unset: {...}})` clearing all 4 `*Palette`/`*PaletteSource` fields — scoped to Harkirat's own account only, per `[[feedback_cache_invalidation_on_algorithm_change]]` (an earlier session in this same feature got this wrong once already with an unscoped `updateMany({})`, correctly blocked by the safety classifier).
2. **Bot-wide interaction timeouts, unrelated to colors specifically.** Render logs from Harkirat's actual testing window showed `DiscordAPIError[10062]: Unknown interaction` (Discord's 3-second ACK window blown before `deferReply()`/`deferUpdate()` even ran) — not just on `/colors`, but on `/manage`, `/settings`, and a select-menu click too, spread across ~15 minutes with zero process restarts in between (ruled out Render free-tier sleep/wake cycling as the cause). Root cause: `kMeansCluster()` ran fully synchronously from start to finish with no `await` inside its iteration loop — on Render's free tier (0.1 shared CPU), this blocked Node's single event loop long enough that ANY other in-flight interaction, regardless of which command, could miss its ACK window while a color extraction was still crunching. Confirmed the mechanism directly: a `setInterval(5ms)` timer fired **zero** times during a pre-fix extraction call and 12 times (matching `KMEANS_ITERATIONS`) after the fix. Fixed by `await`-ing a `setImmediate()` after every k-means iteration (`kMeansCluster` and `getColorPalette` both had to become properly awaited end-to-end — the call site in `getColorPalette` wasn't awaiting it at all before this) and dropping banner's fetch size from 512px to 256px (halves Jimp's synchronous decode/unfilter work; k-means only ever samples ~2500 pixels regardless of source resolution, so this isn't a visible quality loss). This doesn't reduce total CPU time spent — it stops that time from monopolizing the event loop in one unbroken burst, so a concurrent command's `deferReply()` gets a chance to fire in between. **Deliberately NOT a Render plan upgrade** — Harkirat's explicit call: try making the code more efficient first, defer parts of the feature next if that's still not enough, only fall back to touching infra/plan as a last resort.

**Second pass (2026-07-13, on Opus 4.8) — the efficiency rewrite that actually addressed the CPU root cause, not just the yield symptom.** The first pass above made extraction *yield*; this pass made it do far *less* work. Four changes, in order of impact:
1. **Lazy per-source extraction (the headline fix).** `refreshAllPalettes` was renamed to `getPalettePanelData(interaction, prefs, activeSource, forceRefresh)` and now extracts the palette for ONLY the source being displayed, not all four. `buildColorPalettePanel` only ever renders one source's swatches at a time (`data[effectiveSource]`), so extracting avatar+banner+decoration+ nameplate on every render was ~4x wasted work — each a synchronous Jimp decode + k-means pass, and decoration additionally spawning an `ffmpeg` subprocess for its still frame. Every source the user HAS still gets its availability key + preview URL surfaced (cheap — from `getSourceImageInfo`'s network calls, no pixel work), so the nav buttons + current preview all render correctly; the other sources extract lazily the moment the user navigates to them. Decoration's ffmpeg subprocess now never runs unless the Deco page is actually opened. The one behavior tradeoff: first visit to each page shows a brief loading spinner instead of being pre-warmed (accepted — far better than freezing the whole bot). All 6 call sites updated (`commands/colors.js`, and handlers/colors.js's `colors_view`/ `colors_page_`/`colors_subpage_`/`colors_refresh_` handlers — refresh calls it twice, before/after).
2. **Removed `/settings`' background soft-refresh entirely** (`commands/settings.js`). It fired an un-awaited `refreshAllPalettes` on EVERY `/settings` open, speculatively warming all 4 sources' caches in the background whether or not the user ever clicked View Colors — a major unconditional CPU drain (4 background extractions + an ffmpeg spawn per `/settings` open) and a prime suspect for why `/settings`/`/manage` themselves showed up in the 10062 logs. With lazy extraction the panel warms on demand anyway, so the pre-warm bought little and cost a lot. Its removal also eliminates the concurrent-`save()` version-conflict hazard it was carefully working around (it used a separate freshly-fetched `prefs` doc for exactly that reason).
3. **k-means early-convergence** (`utils/colorExtract.js`): break the iteration loop once no pixel changes cluster. Output is BYTE-IDENTICAL to running the full 12 (verified — the returned clusters are computed from `assignments`, which is already stable at convergence), so determinism and the Refresh change-detection are fully preserved. **Honest caveat: measured 0% benefit on Harkirat's own avatar** (12 clusters over 2521 pixels don't fully stabilize within the 12-cap there) — it only helps sources that genuinely converge early (the smaller-K nameplate/decoration at K=6). Kept because it's free-when-it-helps / never-changes-output / never-slower, not because it's a reliable win. Do NOT lower `KMEANS_ITERATIONS` from 12 to force a win — that WOULD change output and break the determinism the Refresh button's "same colors?" comparison depends on against already-cached values.
4. **Memoized solid swatch PNGs by hex** (`utils/colorSwatchImage.js`, bounded 256-entry `Map`). A swatch is deterministic per hex and never changes, but the panel re-encoded up to 4 of them on every page/subpage switch. Now encoded once per process per distinct color. The cached Buffer is only ever read (uploaded as an attachment), never mutated, so sharing one reference across renders is safe and doesn't interact with the `sendV2Payload` attachments-replacement fix.
Verified locally: determinism holds (byte-identical across runs), event loop stays responsive during extraction (a 5ms timer fires ~14× mid-extraction vs 0× when it was fully blocking), the panel still renders correctly with an available-but-unextracted source (Banner button shows even when `data.banner` is null), and all modules load cleanly. **Not yet verified live on Render** — the true test is whether 1-source-at-a-time extraction stays under the 3s ACK window on the actual free-tier CPU; watch the logs for fresh 10062s after deploy. If it's STILL not enough, the remaining levers (in Harkirat's stated order of preference) are: defer more of the feature, then move extraction off the main thread (`worker_threads` — moves the CPU burst off the event loop entirely, though it competes for the same fractional core), and only as a last resort a Render plan bump.

**Branch-testing discovery (2026-07-13): the erratic behavior was ALSO multiple bot instances, not only CPU.** The CPU work above was deployed to a `fix/colors-cpu-efficiency` branch (Render's tracked branch temporarily pointed at it — same service, so only one Render instance, no collision from Render itself) for real-free-tier testing. During that test Harkirat saw the panel render *different code versions on different clicks* (an abandoned blank-emoji heading trick + old "Accent Color N" labels on some clicks, current 8-color layout on others) — impossible within one instance. `ps aux` found **three leftover local `node index.js` processes** (started earlier that day in prior debugging, each frozen at a different stale code snapshot) racing the Render branch bot. This is a single-token bot: multiple live instances make Discord hand each interaction to a random one, and they race each other's `deferReply`/`deferUpdate` (10062/40060). **This very likely contributed to the ORIGINAL 10062 wave too**, not just the CPU angle. Fixed by killing the 3 local processes (Railway was already fully removed — its "Offline" CLI status was real, the logs seen were historical). Lesson now in memory (`[[feedback_multiple_bot_instances]]`) and folded into the push flow (kill stray local instances so only the live instance runs). **A permanent single-instance guard was BUILT 2026-07-25** — see `docs/ROADMAP.md`'s entry and `utils/instanceLock.js` — a Mongo heartbeat lock that refuses to `client.login()` if another instance's heartbeat is still fresh, closing this specific failure mode going forward. **Note also:** a `git push`/deploy does NOT stop local processes on its own — they're different machines; only explicitly killing them, or now the lock refusing to start, prevents the collision.
