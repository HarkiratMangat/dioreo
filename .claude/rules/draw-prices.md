# `/draw prices` & `/draw calculator` — rules & history

*Loads when you touch `commands/drawprices.js`, `commands/drawCalculator.js`, `handlers/drawCalc.js`, `utils/drawCost.js`, or `utils/cpPackages.js`. The price data model, the final layout, the Advanced Double Legendary page, and the cost calculator built on top of it. Shared UI builders/pagination: `.claude/rules/rendering-and-ui.md`. Multi-pass redesign narrative: `docs/DEVLOG.md`'s four `2026-07-12` Part A entries. Design spec: `docs/superpowers/specs/2026-08-15-draw-cost-calculator-design.md`.*

## `/draw prices` layout, final correction (2026-07-13)
Took several wrong attempts to land (see `[[feedback_check_sibling_code_before_guessing]]` in memory) — the ACTUAL final, Harkirat-confirmed structure:
- **Container**: title > divider > entries (no divider before pagination) > pagination row > divider > "Switch between..." hint line > region-switch button row. The region-switch button is the container's LAST item.
- **Outside the container, as a separate top-level sibling**: the global nav row (`buildGlobalNavRow('nav_prices')`) — matching `/calendar`'s and `/draws`' own convention of passing the nav row into `withShareButton([containerPayload, globalNavigationRow], isEphemeral)` rather than nesting it. This command is the only one of the three with extra content (hint line + region button) that has to sit BETWEEN the container's own entries and the nav row, but the nav row still ends up last overall, just with no divider needed between it and the container (two separate top-level components already get Discord's own inter-component spacing).
- **No divider between the last entry and the pagination row** — this was explicitly requested multiple times and got dropped by mistake mid-session when a blanket "large divider spacing across the board" pass over-applied; don't reintroduce it.

## `/draw prices`' "Advanced Double Legendary Weapon Draw" — its own 3rd page (2026-07-21)
A new, distinctly-shaped draw type added to `/draw prices` from Harkirat's own 10/30 CP breakdown. It does NOT fit the shared `draws: []` model every other entry uses — it has **three purchase modes per spin** (Regular / Advanced / the "Trap") plus a **strategy breakdown** — so it's given its own builder and its own dedicated page rather than being shoehorned into `DRAW_DATA`/`buildDrawEntries`.
- **Its own page 3.** `SUBPAGES` still holds only the two key-driven pages; the new page lives at `ADVANCED_PAGE_INDEX` (`= SUBPAGES.length`), and `TOTAL_PAGES` (`= SUBPAGES.length + 1`) is what the page clamp and the pagination row now use (were `SUBPAGES.length`). `buildContainer` renders `currentPage === ADVANCED_PAGE_INDEX` via `buildAdvancedDoubleLegendaryEntry(regionKey)` instead of `buildDrawEntries`. **If you add more key-driven pages, push to `SUBPAGES` — `ADVANCED_PAGE_INDEX`/ `TOTAL_PAGES` re-derive automatically** and the Advanced page stays last.
- **Everything numeric is DERIVED, nothing hand-typed** — same rule the rest of this file enforces (see `DRAW_DATA`'s comment). `ADVANCED_DOUBLE_LEGENDARY` stores ONLY the Regular + Advanced per-pull arrays per region. From those: **Trap = always exactly 2× Regular** per pull (Regular spin + buying the 2nd item afterward = two Regular Purchases); all three totals = array sums; the three **strategy costs** = cumulative slices (Reg 1-8 + Adv 9-10 / Reg 1-9 + Adv 10 / Reg 1-10). A wrong number can only ever exist in one place.
- **Rendering reuses the command's existing conventions** — `boldDrawSequence`/`cumulativeSequence` via a `{ draws }` shim (bold ` / `-joined pulls, `⌇` before the total, `-# CP Spent:` cumulative joined by `›`, `cp2` icon on the quote-blocked headline).
- **Layout redesigned 2026-07-21 (v2.30.0) to match Harkirat's own hand-drawn mockup** (`local/advanced leggy_format.json`), then **corrected 2026-07-21 (v2.30.1, committed but NOT yet pushed/deployed as of this writing)** after a marked-up screenshot from Harkirat (`local/Screenshots/CleanShot 2026-07-21 at 20.16.48@2x.png`) flagged two mistakes in the v2.30.0 version. Current (corrected) shape — the whole entry is a flat run of Text Displays with **NO internal dividers**: **headline** (full-caps name + Reg/Adv totals + `(See **The Strategy** below)` pointer) → **3 purchase modes** (`'Regular Purchase' Only` / `'Advanced Purchase' Only` / `'Regular Purchase' + Remaining Item Separately`) → **1 callout** (`THE TRAP`; the `NOTE` callout was removed entirely 2026-07-25 per Harkirat's request) → **The Strategy** as THREE separate Text Displays (each strategy line carries an inline `cp2` icon on its cost). 8 Text Displays, 0 internal dividers.
  - **The two v2.30.1 corrections:** (1) the v2.30.0 builder added three spacing-2 dividers (`dividerBefore = {1,4,6}` — after the headline, after the purchase modes, after the callouts) that were **never in the mockup**; removed entirely (`buildAdvancedDoubleLegendaryEntry` now just `blocks.map(c => ({type:10, content:c}))`). The ONLY dividers on this page are the title divider above the headline and the footer divider below, both added by `buildContainer`, not the entry builder. (2) the strategy heading was `### **The Strategy, If You Want...**`; Harkirat's exact correction is a plain bold line with a period: **`**The Strategy. If You Want...**`** (no `### `, comma → period). **⚠️ SUPERSEDED 2026-08-07 12:21 EDT** — Harkirat asked for the opposite: the heading is now a real `### The Strategy` (no bold, no "If You Want..." — each strategy line's own bold label already states the condition). Applies to both the Weapon and Character pages. Don't "correct" it back to the plain bold form; that was the v2.30.1 call, this reverses it deliberately.
  - The mockup only drew the 10 CP region — the 30 CP region is the same design fed its own derived numbers. Re-verified via a `buildContainer()` JSON dump after the correction: the container has exactly 2 dividers (title + footer), every total re-sums correctly, and every page/region stays well under the 40-component cap (Advanced page ≈ 26 incl. nav + share).
- **All draw-price entry headings are FULL-CAPS** (2026-07-21, v2.30.0) — both the two key-driven pages (`buildDrawEntries`, via `meta.name.toUpperCase()`) and the Advanced page. `DRAW_META.name` stays the canonical mixed-case source of truth; only the rendered heading is uppercased. ## `/draw prices` gains a 3rd region + a 4th page: the Advanced Double Legendary Character Draw (2026-08-07)

- **`REGION_ORDER = ['region_10', 'region_20', 'region_30']`** is now the single place that enumerates "all regions in order" — both the 3-way region switcher and `execute()`'s `defaultRegionMode` resolution read from it, so a hypothetical 4th region only needs to change this one array plus its `DRAW_DATA`/`ADVANCED_DOUBLE_LEGENDARY` keys.

  - **Each button carries its own per-region icon** (2026-08-07 15:46 EDT, from Harkirat's own notes-file request) — `region10Cp`/`region20Cp`/`region30Cp` in `emojiMap.js`, looked up per render via `REGION_EMOJI_KEY[key]` (a `{region_10: 'region10Cp', ...}` map right below `REGION_ORDER`). Replaces the single shared `regions` icon all three buttons used to carry identically; `regions` itself is left defined since nothing else in the codebase references it.
- **`doubleEpicCharacters.region_20` is deliberately `null`** — no real data exists for that draw at ANY region beyond 10 CP (not even 30 CP), so there's no second data point to interpolate from even if a guess were wanted. Harkirat's explicit call: leave it null (renders the existing "haven't done the research yet" placeholder) rather than ship a speculative estimate as real pricing.
- ~~**`mythicWeapon`/`mythicCharacter` have no `upgrade` field at `region_20`**~~ → **they do since 2026-10-16 11:14 EDT** (Harkirat: Mythic Card 1,000 CP × 10 for the weapon, Mythic Coins 1,170 CP × 14 for the character). Historical note follows: — the source screenshots only gave per-pull draw totals, not the separate Upgrade cost, so there's no real number for it yet. `buildDrawEntries`' `if (entry.upgrade)` check means the Upgrade line just doesn't render for these two entries in the 20 CP region until real data turns up.

  - **The reward framing is genuinely different, not a Weapon→Character find/replace.** Harkirat clarified (2026-08-07) this draw's two prize pairs are BOTH Legendary tier — 2 Legendary Characters (this banner's own headline reward) and 2 Legendary Weapons (the secondary Advanced-purchase reward) — unlike the Weapon page, whose secondary reward is 2 EPIC characters. Don't re-derive this from scratch if it comes back up — the formula above is already correct, just unused. Never guess a strategy tier's pull sequence from cost alone; this one required Harkirat to specify the exact reg/adv split, because "regular first, then switch to advanced" doesn't cover every real spend pattern (this one splits regular before AND after a single advanced pull).

## `/draw calculator` — the live cost panel (built 2026-08-15, rebuilt 2026-08-26 11:20 EDT)

Answers "I've done N pulls — how much more CP do I need, and what's the cheapest way to buy it." Two pure, independent engines (`utils/drawCost.js` for draw remainder math, `utils/cpPackages.js` for the package table + purchase optimizer) sit under **one** Components V2 panel (`commands/drawCalculator.js` + `handlers/drawCalc.js`). Original design: `docs/superpowers/specs/2026-08-15-draw-cost-calculator-design.md`; the nine-task build log: `docs/superpowers/plans/2026-08-15-draw-cost-calculator.md`.

### 🔴 SIXTH PASS, 2026-08-27 12:00 EDT — the saved-basket redesign is BUILT (not "designed, not built" any more)

The single-draw goal/budget mechanics this section used to describe in detail (F/P/B target modes, `buildCostBreakdown`/`buildBudgetBreakdown`, `clampStateToDraw`, a fully stateless customId with no model at all) are **GONE, replaced wholesale** by `docs/superpowers/specs/2026-08-27-draw-calculator-multi-draw-design.md` (revision 3) and its plan. Read the spec before touching this file further — this section is a pointer to it, not a duplicate.

🔴 **The basket is a FLAT LIST OF BANNERS. "Quantity" does not exist.** Three Mythic Weapon banners are three independently-orderable rows in `basket.banners`, each with its own `pullsDone`. There is no goal select (Finish/Stop-at-pull/Budget) any more — every banner is always priced to completion; budget mode and per-banner goals other than Finish are explicitly out of scope (spec §10).

### 🔴 SEVENTH PASS, 2026-08-27 19:20 EDT — Harkirat rejected the shipped panel's UX; vocabulary and structure DECIDED, structure NOT YET BUILT

He opened the sixth-pass panel and called it "terrible for user intuitiveness." Six concrete bugs were fixed the same day (below); two decisions were taken that this file's own earlier text contradicts, so read these before trusting anything further down.

- 🔴 **PLAYER-FACING VOCABULARY: the saved thing is a "calculation", one row in it is a "line".** Harkirat's own word ("reset/new calculation"), after rejecting Basket, Plan, Draw List, Banner, Watchlist, Grind List, Push, Run, Quote, Order, Tab and Tracker across five rounds. The reframe that settled it is worth keeping: *"the player is not grinding, they are PURCHASING something and calculating pricing and budget for it"* — so container metaphors (basket/cart/list) were all wrong in the same way, and progress metaphors (watchlist/tracker) were wrong in the other direction. "Line" is **provisional**; he expects to revisit it. "Banner" is permanently out — it collides with Discord profile banners, which this bot also renders.
- ⚠️ **INTERNAL identifiers deliberately keep the old names** — `models/DrawBasket.js`, `utils/drawBasketStore.js`, `basket`, `banners`. Renaming them would churn `PRIVACY.md`, the store, the collection and every test for something no user can see. **Do not "finish" the rename into the model layer.** Only strings a player reads are in scope.
- 🔴 **THE LANDING PAGE BECOMES A REAL SETUP FORM — this REVERSES this file's own "never a setup form again" rule, deliberately and with Harkirat's explicit approval.** His words: the landing should be *"the primary space to collect all info before the user submits and gets their breakdown,"* with the breakdown page's controls existing to *adjust* those values afterwards. Two qualifiers make it not a repeat of the failure that produced the old rule: the saved calculations list and the setup form share **one** first screen (no extra hop to reach either), and the result **persists until the player hits reset / new calculation** — so it is filled in once, not re-filled on every visit. The original rule came from a single-draw panel where five interactions preceded any figure at all, *every time*. **BUILT 2026-08-27 21:2x EDT.** `buildSetupPanel` is the first screen; `submitted` on `models/DrawBasket.js` is what separates a draft from a result, so a result survives a restart and persists until **New Calculation** (the old `Reset`, relabelled — same two-step `resetarm`→`reset` verbs, now also clearing `submitted`). `Calculate` (verb `submit`) is the ONLY Primary-styled button in the command.

**State lives in TWO places now, on purpose.** The customId (`commands/drawCalculator.js`'s `encodeState`/`decodeState`) carries only view state — `calc~<verb>~<basketId>~g<page>~x<detail>~f<focus>~a<authorId base36>`, plus two OPTIONAL trailing fields (`p<bpage>`, `r<targetRegion>`) most controls never pay for. The basket itself (banners/region/balance/includeUpgrades/entitlementMask/name) lives in `models/DrawBasket.js`, read and written through `utils/drawBasketStore.js` — the ONLY module that touches that collection directly. 🔴 **The "stateless by design" claim this file used to make no longer holds** — a basket persists to Mongo and can go stale (deleted, or an unnamed one past its 30-day TTL). Every render path takes `basket` as an explicit possibly-null argument; `handlers/drawCalc.js`'s `loadOwned()` is the one place ownership + existence are resolved, and every basket-touching branch routes through it.

- 🔴 **`SETUP_LINES_PER_PAGE` is 4 while the Edit page's `MAX_BANNERS_PER_PAGE` is 5, and that difference is a MEASURED budget fact, not an inconsistency.** The setup screen also carries the saved-calculations list, the draw multi-select, the region row and the Calculate row. The sweep in `scripts/drawCalcBudget.test.js` covers 0-9 lines × saved-list present/absent × three pages; change either number and it tells you immediately. ⚠️ **SUPERSEDED 2026-10-13 23:13 EDT:** the Edit page is gone and the form pages at 6 lines (one dropdown per line), dropping only when the saved list makes it not fit. See § THE REDESIGN.
- 🔴 **Pagination and "+ Add another" are never both rendered on the setup form.** With five or more lines the screen is at its densest, the multi-select still adds new TYPES, and a duplicate line can be added from Edit Draws after calculating. Showing both overruns the 40-cap. ⚠️ **SUPERSEDED 2026-10-13 23:13 EDT:** "+ Add another" is gone; "+ Add more draws" renders under the lines on every page of the form.
- 🔴 **The setup form's picker is a MULTI-select, so `handlers/drawCalc.js`'s no-basket `draws` branch must map EVERY `interaction.values` entry to a line.** Reading `values[0]` (what the retired single-pick landing did) silently drops every draw after the first — a wrong result that looks like a working one.
- **`drawSelectRow` is gone** — the multi-select replaced it, and inherited its richer option descriptions (pull count + full fresh cost at this region + upgrade), because the setup form's picker is now the only place a player chooses what to price.
- **The COST BREAKDOWN block LEADS with `CP Needed`.** It used to open with a "Draws in basket" count and put the one number the command exists to produce third; the count is deleted outright, since the list directly above already shows every line.
- **Two pages.** *(The "not a setup form" this bullet used to assert was reversed 2026-08-27 — see the seventh pass above. The two-page shape below is what is BUILT today, not what was last approved.)* Page 0 (`g0`, COST) shows the basket listing, cost breakdown, priority plan and recommended package. Page 1 (`g1`, BASKET) shows one pulls-done dropdown per banner (🔴 every option AND the placeholder carry the banner's number, `#N —`, since a select's placeholder is replaced by the chosen option), paginated at 5 for readability (9 would fit the component budget). Reordering is the ONE remaining focus pointer — a single select (`setfocus`) plus `▲`/`▼` buttons, never a per-banner button pair (that would cost a whole extra Action Row per banner).
- 🔴 **Never reuse `buildDrawEntries()` on Page 0 or Page 1** (measured 52/40 for nine draws — a hard send failure) — but `Draw Info` (its own ephemeral message, own fresh 40-component budget) reuses it at full fidelity for every DISTINCT draw type in the basket. Not a contradiction: the 40-cap is per MESSAGE.
- 🔴 **The bottom nav row is a TOP-LEVEL SIBLING of the Container, never one of its children.** `buildCalculatorPanel` returns the message's whole component list (`[container, bottomNavRow]`) and is the ONE place that attaches it; page builders must never push it into their own `components`. It shipped nested once and rendered boxed inside the panel's accent border, which is not how any other command in this bot places its nav — pinned by a falsifiable case in `scripts/drawCalcBudget.test.js`.
- 🔴 **Never write `DRAW_META[b.drawKey].name` for a key that came out of a STORED calculation — use `drawName()`.** `DRAW_KEYS` is derived from `DRAW_META`, so anything rendered from a select is safe by construction, but a saved calculation holds whatever key it held on the day it was saved and draws rotate. The day a key leaves `DRAW_META`, every stored calculation containing it would throw on render and its owner could not even open the panel to delete the row. `drawName()` degrades to the raw key instead; `buildDrawInfoPanel` filters unknown keys out entirely, and `addDrawsRow` only ever lists the keys `DRAW_META` has, since `buildDrawEntries` indexes `DRAW_META` directly.
- **No emoji on the nav row or the Save/Delete row** (2026-08-27, Harkirat) — `utils/globalNav.js`'s `NAV_ITEMS` carries none on any slot, so `/draw prices`' "Draw Calculator" override must not add one either, and `mngEdit` (a pencil) never matched a button labelled "Save".
- 🔴 **Store `drawKey` STRINGS in the basket document, never positional indices** — an index silently re-points a stored basket at a different draw if `DRAW_DATA`'s order or length ever changes.
- 🔴 **`PRIVACY.md` §2.1d + Appendix A were shipped in the SAME change as the model** — `docs-audit`'s `privacy-model-coverage` enforces this, and it is the gate working, not an obstacle.
- **Region switching preserves every banner's progress** (`regionRow`/the `region` verb only ever touches `basket.region`) — an unpriced banner at the new region is excluded from the total and NAMED on its own line, never silently dropped.
- **Reset is two-step** (`resetarm` → `reset`, Danger-styled once armed) and clears `banners`/`balance`/view state, but never the basket document or its name. **Delete Basket is two-step the same way** (`delarm` → `del`) and DOES remove the document — the two are deliberately different weights of destructive action.
- **Naming a basket IS saving it** — the manage row reads `Save` on an unnamed basket, `Rename` once it has a name; either opens the same one-field modal (`modal_name` → `nums_name`), and `utils/drawBasketStore.js`'s `rename()` is the only function that ever touches the `name` field (a generic `save()` deliberately never does, so it can never accidentally clear a name it wasn't given).
- **"Show Everyone" publishes a SNAPSHOT, not a live copy** (design decision 10) — `handlers/share.js` detects a `calc~` custom_id anywhere in the shared message and strips every Action Row from the Container while leaving every Text Display untouched, so the cost breakdown stays fully readable with nothing left to click.
- **Author lock via `resolvePanelActor`**, never a bare id comparison — a denied click gets an explicit lock message and never touches the basket store (`handlers/drawCalc.js`'s `route()`, tested in `scripts/drawCalcBudget.test.js`).
- **No passive expiry** (`skipExpiry: true`) — ⚠️ **this was decision 7 but was NEVER ACTUALLY WIRED until 2026-08-27**; this file and the memory store both asserted it held while zero `skipExpiry` occurrences existed in either file. Re-derived against `sendV2Payload`'s own stated bar ("nothing on this panel can go stale") before wiring it: every control re-reads the calculation from Mongo on each click, and a component click carries its own fresh interaction token, so the message can be edited indefinitely and never shows a frozen view. Its justification changed with the store: it now rests on the basket document being the source of truth, not on the customId being self-contained. Do not "restore" expiry on the reasoning that the panel can go stale; the missing-basket path handles that instead.
- **The command name did NOT change** — still a subcommand of `draw`, `drawCalculator.js` still exports no `data`. `utils/globalNav.js`'s `overrides` param is STILL used by `/draw prices`' own cross-link button (now pointing at the calculator's plain landing state via the `page` verb, since there is no `region` field on the calculator's own state to target any more) — do not delete it.
- **Verified by `scripts/drawCalcBudget.test.js`** (component budget swept across basket size 1-9 × page × detail, the no-null/NaN/undefined/negative sweep, the falsifiable no-algorithmic-reordering proof, banner-number-prefixed dropdown options, the two-step confirms, region preservation, the share-strip, and the author-lock denial) plus `scripts/drawBasketStore.test.js` (ownership on every store operation, against a stubbed model). **Not yet click-tested live in Discord by Harkirat** — that is his own next step, not a gap in the automated coverage.

### 🔴 EIGHTH PASS, 2026-10-13 12:42 EDT — Harkirat's click-test: 19 fixes and a visibility setting

He click-tested the setup form on the dev bot and asked for a harsh first-time-user critique (`local/project/features/draw-calculator/critique-2026-10-13.md`, gitignored); he approved all 19 fixes. The four that changed behaviour, not wording:

- 🔴 **Running the command REOPENS the most recent calculation** (`utils/drawBasketStore.js`'s `latestForUser`, sorted on the new `updatedAt`). Before, `execute()` always opened an empty form and `listForUser` lists NAMED calculations only, so an unsaved result could not be reached again: the "persists until New Calculation" promise the setup form was approved on did not hold past one message. `/draw prices`' cross-link (no basketId) reopens it the same way via `loadOwned()`. **Do not "simplify" `listForUser` into including unnamed ones**: the picker is for kept calculations; the latest one opens by itself.
- 🔴 **Draw Prices opens `/draw prices` as its own private message** (verb `prices`), like Draw Info. It used to be the global nav's `nav_prices`, which replaced the calculator in place. ⚠️ **SUPERSEDED 2026-10-13 23:13 EDT:** Draw Info is no longer on the nav row (his intake); its `info` verb still answers panels posted before.
- 🔴 **Unticking a draw that has progress asks first** (`dropConfirmRow`; the requested selection rides in an optional `m` mask field over `DRAW_META`'s key order). It used to delete every line of that draw, pulls and all, on one untick.

### 🔴 THE PURCHASE OPTIMIZER'S TWO METHODS (rewritten 2026-08-27 00:07 EDT)
`utils/cpPackages.js` returns `{ cheapest, absoluteCheapest, stockUp, naive }`. Two things changed and both were live defects Harkirat found by reading a real panel, not by any gate.

- 🔴 **`LEAST_WASTE` IS GONE AND MUST NOT COME BACK.** It read `(a.cp !== b.cp ? a.cp < b.cp : a.cents < b.cents)` — minimize CP *obtained*, money only a tie-break — so it would pay anything to shave the overshoot. Measured on the real table at 11,510 CP in CAD: it swapped one 10,800 pack for five smaller ones to drop leftover from 30 CP to 10 CP, for **CA$26.00 more**. Harkirat's reasoning is why it is deleted rather than tuned: *"those extra CP still have value and they can be used in the future"* — leftover is banked value, not waste, so the objective optimized the wrong quantity. A test pins its absence, because it is exactly the kind of comparator a later session would "restore" as an obvious gap.
- 🔴 **`cheapest` IS DELIBERATELY NOT THE ARITHMETIC MINIMUM.** The 6-transaction cap alone was not enough — the DP spent its whole budget chasing pennies. At 11,510 CP in CAD the true optimum is `4x80 + 1x420 + 1x10800` = CA$140.94 across **six** store purchases, while `1x880 + 1x10800` is CA$142.98 across **two** — CA$2.04 more for four fewer purchases *and* 140 more CP. `cheapest` is now the **fewest-purchase** combo within `TRANSACTION_TOLERANCE_PCT` (3%) of the optimum, floored by `PRACTICAL_MAX_TX` (6) so a caller passing a loose `maxTransactions` still cannot be shown a 63-purchase answer. The true optimum stays as **`absoluteCheapest`**, exported so a test can pin exact arithmetic — a tolerance assertion alone cannot tell a working search from a broken one.
- **`stockUp` replaces Least Waste and points the other way**: best CP-per-unit-money within 1.6× the practical cost, ≤3 purchases, and only when it beats the practical rate by ≥3% *and* banks more CP. **It returns `null` most of the time and nothing renders — that silence is the feature.** A second method forced to appear every time has to manufacture a difference, which is precisely how Least Waste ended up recommending a CA$26.00 premium for 20 CP.
- ⚠️ **`findStockUp` brute-forces rather than using the DP, on purpose.** Its objective is a RATIO (`cp / cents`), which has no optimal substructure — the best-rate route to 10,000 CP is not built from the best-rate route to 5,000 — so a DP over it would be quietly *wrong*, not merely slow. The space is tiny (multisets of ≤3 from 6 packages × ≤64 entitlement subsets).
- ✅ **2X mixing was verified correct, not assumed.** Harkirat asked whether it can ever recommend the top pack at 2X *and* the same pack again at the normal rate. Measured: at a 26,000 CP shortfall with the `cp8000` entitlement it returns exactly `1x cp8000(double) + 1x cp8000(normal)`. The mask-subset enumeration over entitlements plus the unbounded normal-package DP supports this structurally; no fix was needed.
