# The thinking pass — HOW, not just when

*Written 2026-09-06 14:53 EDT, after Harkirat asked how many times he has had to supply this. **Measured across 174 session transcripts: 599 instructions, in his own words.** The WHEN was already written down in three places. The HOW was written down nowhere, so he has supplied it by hand, every session, for over a month.*

🔴 **THE TOOL THIS FILE MEANS, NAMED ONCE SO NOTHING BELOW HAS TO GUESS — flagged as an ambiguity gap 2026-09-07 12:28 EDT, after this file had already been read and cited several times in the same session without ever saying so.** Every "the tool"/"it" below refers to **`mcp__sequential-thinking__sequentialthinking`** — the sequential-thinking MCP tool, invoked directly as a tool call (`thought`, `nextThoughtNeeded`, `thoughtNumber`, `totalThoughts` parameters). It is NOT `superpowers:brainstorming`, not the `doc-coauthoring` reader-test lens, not `systematic-debugging`, and not a generic instruction to "think carefully" in prose — those are different mechanisms this repo also uses, for different jobs. This file governs one specific tool call.

## The pass, in his words

1. **Pre-emptively, not afterwards.** Before the work, not as a verification ritual after it. *"invoke and use sequential thinking frequently and pre-emptively, not afterwards"* (2026-08-27).
2. **Do not UNDERUSE it — that is the whole point, and the number is not the rule.** Harkirat, 2026-09-06 14:58 EDT, correcting this line: *"15+ thoughts is for a large, basically end of session run. every run doesnt need 15+ thoughts. the key insight is to not underuse the tool."*
   - **Length follows the question.** A fork between two known options is a few thoughts. A plan, an audit, a compact-prep or an end-of-session review is where 15+ belongs.
   - **One thought is never a pass.** *"Not once have i ever seen a session use it for 1 thought."* A single thought is a label on a conclusion already reached.
   - ⚠️ **Do not turn this into a quota.** Padding to a number is the same failure as skipping it — both substitute a count for the work.
3. **Question everything harshly.** Attack the premise, not only the plan built on it.
4. **Challenge your own thoughts** as they arrive. Steelman the objection to your own answer before presenting it.
5. **Ask the unasked question.** The one nobody in the thread has raised, including him.
6. **Check the unconsidered angle.** Name the angles NOT taken, then take one.
7. **Find gaps and staleness.** His most-repeated clause. Assume something you are relying on has already been superseded, and go look rather than recall.
8. **Falsify yourself.** Construct the case that shows you are wrong. A check that cannot fail is not a check.
9. **Do not re-ask what he already answered.** *"Don't ask questions that are just rephrased versions of things"* already settled.

## A third failure mode, found by actually running the pass — 2026-09-07 12:26 EDT

*Not theorized — measured in one real handoff-prep pass, with Harkirat pushing back three separate times before it held. Distinct from the two failure modes below: those are about WHEN a pass runs; this is about what makes a pass that DID run before the deadline STILL fall short.*

- 🔴 **STOPPING AT A PLAUSIBLE COUNT IS NOT THE SAME AS RUNNING OUT OF QUESTIONS.** A pass stopped at 11 thoughts — inside "10-15+," short of the stated "15+ at least" — because momentum moved to executing fixes, not because the questions ran dry. Pushed to continue, thought 13 (past where it had already stopped once) was the sharpest of the whole run. **The number was never the point; treating a number as sufficient is the failure.** The only real stopping signal is the LAST few thoughts finding nothing the FIRST few didn't — never a count.
- 🔴 **AN INTERRUPTION IS NOT A COMPLETION.** Real messages arriving mid-pass with unrelated, legitimate corrections got handled correctly — and the pass was then silently treated as done because forward motion had moved on to writing the deliverable. **A pass interrupted by reactive work needs an explicit RESUME, stated as such, not an implicit close.**
- 🔴 **"DID I VERIFY X" QUESTIONS ARE CORRECT AND NECESSARY — AND MUST NOT BE THE WHOLE PREMISE.** Self-audit ("did I verify claim X I already made") is real work and found real defects. But it is not what "ask the unasked question" means. Harkirat, naming this directly: *"why 'did i verify X' questions are correct, they shouldnt be the entire premise of the sequential thinking run... uncomfortable, hard, harsh, provoking, scrutinizing, deep/rich questions are important and necessary as well."* The question that found the sharpest defect this run was neither — it was **"is there ONE thing underneath these N separate findings"**, asked only after the checklist-mode questions had been exhausted.
- 🔴 **A CLEAN UNIFYING NARRATIVE IS ITS OWN THING TO FALSIFY.** Reframing five mistakes into "one root cause" felt like insight and was itself not fully honest — one of the five instances didn't actually fit the unifying story, and folding it in anyway to make the write-up tidier was reaching for the cleaner narrative over the messier true one. **The pass that produces a satisfying unifying answer is not done; stress-test the unification itself before writing it down**, the same way any other claim gets stress-tested.

## A fourth failure mode, found 2026-09-08 across multiple sessions and repos, and live in the SAME session that wrote this fix

*Not one instance — a pattern found by actually searching transcripts, per Harkirat's own instruction: "search for instances in your recent transcripts and you'll see the pattern." It held. Grep across the last 21 days found this shape repeating in Diors-Builds AND Devoid, under different wording each time: "are you sure?", "did you ask the easy questions dressed up as hard ones?", "are you sure this is your best work?" — always followed by a real finding the pass had not surfaced on its own.*

🔴 **THE ROOT CAUSE, IN A PRIOR SESSION'S OWN WORDS, PRAISED BY HARKIRAT AS THE SHARPEST SELF-THOUGHT IT HAD PRODUCED, AND THEN NEVER WRITTEN DOWN HERE:** *"my verification effort scales with pushback rather than self-discipline."* That session found it after being pushed once, and wrote it into `docs/reference/session-handoff-guide.md` §3f the same day — correctly, but into a file read only when preparing a handoff, not the always-loaded layer. This file existed too and never carried it, so it still had to be rediscovered from a transcript rather than from either place it should have been findable. **That is the gap this section closes: promoting an already-written lesson into the layer that reaches every session, not discovering it for the first time (corrected 2026-09-08 21:32 EDT after finding it already in the guide while doing unrelated handoff work).**

- 🔴 **THE FIX IS NOT "TRY HARDER" — IT IS TO PRE-EMPT THE PUSHBACK QUESTION ITSELF.** Before presenting any check, audit, or "done" claim, ask literally: *"if Harkirat looked at this right now and said 'are you sure? did you ask the easy questions dressed up as hard ones?' — what would I go check next?"* Then go check THAT thing immediately, in the same pass, before presenting anything. The question that would come after pushback is knowable in advance; the only reason it usually isn't asked until after is that asking it costs nothing to skip and pushback is what makes skipping visible.
- 🔴 **A BURIED FINDING IS NOT A SURFACED ONE.** Devoid, 2026-09-07 19:42 EDT: a session's own summary correctly noted "v1.0.0 is released but anonymous GitHub answers 404" — genuinely the most important line in the report — and buried it as one bullet among many, asking no question about it. Harkirat: *"arguably the most important line in your summary and you buried it. Nor did you ask any question about it."* Finding the hard thing and then presenting it with the same weight as everything else is a milder version of not finding it at all — rank findings, and lead with the one that would make him say "wait, that's the actual problem," not the one that's easiest to write up cleanly.
- 🔴 **A PARAPHRASE OF SOURCE MATERIAL IS A NEW, UNVERIFIED CLAIM — DIFF IT AGAINST THE SOURCE, NOT AGAINST YOUR MEMORY OF WRITING IT.** Found 2026-09-08 during this exact fix's own WP6 work: rewriting a 2,584-byte historical span into cleaner prose for `docs/reference/portal-decision-ledger.md` silently dropped a caveat ("this count is no longer the floor, corrected 2026-09-03") and stated a stale number as settled. `docs-audit`, the reflow gate, and re-reading the new prose for fluency all passed — none of them check fidelity to a source that no longer exists in the output. **The only check that caught it was actually diffing the new sentence against the extracted original text, fact by fact**, not re-reading the new version and judging whether it *sounded* right.
- 🔴 **LIVE, CAUGHT MID-BUILD OF THIS VERY SECTION — AND IT HAD A SECOND LAYER THE FIRST CHECK MISSED TOO.** Deciding between `ctx_execute` and plain Bash+`python3` for searching transcript files outside the project root, the reasoning written down was *"given the uncertainty, I'll just fall back to plain Bash."* Harkirat: *"you deciding a muscle memory tool and the reason you decided it. That's preventable."* First correction: one real call showed `ctx_execute` DOES read outside the project root (only `ctx_execute_file`'s `path` argument is guarded — Issue #852 in the plugin's own source, `server.ts`/`security.ts`). **That looked like the finding — and it was still shallow.** Harkirat, again: *"feel like you diagnosed it incorrectly and didn't search the correct things."* The actual gap: `ctx_execute_file`'s guard checks the SAME `permissions.allow` `Read(...)` rules the host already reads — and `~/.claude/settings.json` already had `Read(/Users/harkirat/.claude/projects/**)` configured, covering the exact path being searched. `ctx_execute_file` would have worked fine, inside the plugin's own security boundary, and nobody checked the one file (`settings.json`) that would have shown it. **Two layers of the identical failure, back to back, in the same investigation**: first, an uncertainty resolved by assumption instead of one call; second, a real finding treated as complete before checking the one remaining place — the project's own config — that the finding's own logic pointed at. **A check that stops at the first real answer is not yet the check.**

**The one question this section adds to the pass, stated so it can be checked rather than merely intended:** *before presenting a check, a claim, a summary, or a tool choice, name the pushback it would draw — then spend the one cheap call that pushback would eventually force, now, instead of waiting to be asked.*

## A fifth failure mode, and it is the one that let a nine-hour rule violation through — 2026-09-10 20:02 EDT

🔴 **THE PASS SEARCHES THE SPACE YOU WERE ALREADY THINKING ABOUT, AND CALLS THAT A SWEEP.** Measured, not theorised: a compact-prep pass ran five thoughts, explicitly asked *"where will this handoff be wrong?"*, and produced four answers — every one about the portal work that had filled the session. **Not one was "it omits the output style that loads on every turn."** The session had broken the Silent contract **39 times** by then: mid-run prose against a four-item exception list, 9 of 13 final messages over budget, 11 chapter marks across 176 messages. None of it surfaced until Harkirat asked, two messages after I declared the compact ready.

**The rules that govern EVERY turn are the ones a pass never reaches, precisely because they are not what the session was about.** `silent-mode.md` and this file both declare `unconditional: true`. They were in context for all 176 messages and neither was examined once.

🔴 **So the pass carries one fixed question that is not about the task: WHICH RULES LOADED UNCONDITIONALLY THIS SESSION, AND WHAT IS MY MEASURED COMPLIANCE WITH EACH?** A number, never a judgement — "I think I kept it tight" is the answer that produced 39.

- **For the Silent contract there is an instrument and it takes seconds:** `node scripts/summaryShape.mjs --session latest` reports this session's mid-run prose, final-message median and p90, count over budget, and tables per message. ⚠️ **It could not measure silence at all until 2026-09-10 20:01 EDT** — it was built the day the complaint was "walls of text", so it counted final-message shape and ignored the rule the contract lists first. An instrument inherits the complaint that created it; ask what it does NOT measure before trusting a clean row.
- **For this file, the check is the thought log itself:** did the pass ask anything that was not downstream of the task in front of it?

⚠️ **And the cheap tell that the question was skipped: the pass produced only findings you could have listed before running it.** A pass whose every answer is about the work at hand has not swept — it has elaborated.

## Two failure modes this file exists to stop

- 🔴 **Thinking AFTER, to verify a conclusion already reached.** That is a ritual, not a pass. The thoughts must be able to change the answer, which means they run before it is formed.
- 🔴 **Dispatching an auditor instead of auditing.** *"Dispatching an auditor is not auditing"* — see [[feedback_substituting_the_near_neighbour]]. A subagent's report is input to your pass, never a substitute for it.

⚠️ **The tool is unrestricted, permanently, by his own measured decision.** Cost is not a reason to skip it and never was. The only reason it has been skipped is that reaching for it was left to memory instead of being written down as the default shape of any judgement call.
