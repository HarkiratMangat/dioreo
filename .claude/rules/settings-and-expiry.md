# `/settings` — author-lock, passive idle-timeout, admin override

*Loads when you touch `commands/settings.js` or `utils/passiveExpiry.js`. The per-user panel locks (also covering View Colors / `/colors`). The `/manage` admin-only guard is separate — `.claude/rules/manage-panel.md`. Accent-style options: `.claude/rules/accent-and-colors.md`. The `/settings` 2-page layout + region-mode history: `docs/DEVLOG.md` → *"2026-07-12 — The batch refinement pass: three panels rebuilt, and an Edit crash traced to `setValue(undefined)`"*.*

## Panel interaction locks — `/settings` (author-lock + passive idle auto-disable)
Original gap (2026-07-14): `/settings` had NO author-lock on some components (`set_page_` carried no `userId`) and no expiry mechanism existed anywhere in the bot. (`/manage`'s own separate admin-only guard is documented in `.claude/rules/manage-panel.md`.)
- **`/settings` fix (original, 2026-07-14): author-lock via `|userId` on every custom_id**, plus a REACTIVE expiry (a deadline value encoded as a further pipe segment, checked on click, replying "run `/settings` again" if stale). **⚠️ The expiry HALF of this is SUPERSEDED (2026-07-18) — see the "Passive idle-timeout auto-disable" subsection right below.** The author-lock (`|userId`, checked in every `toggle_`/`set_`/`set_page_`/`colors_view` handler) is UNCHANGED and still exactly as described here; only the expiry mechanism was replaced. `set_page_` also needed a real fix of its own at the time: its custom_id used to be a bare `set_page_{N}` with no pipe segments at all, so adding `|userId` required switching its parsing from a blind `.replace('set_page_', '')` to a proper `.split('|')` — that part is also unchanged.

### Passive idle-timeout auto-disable (2026-07-18) — replaces `/settings`' old reactive expiry
The reactive design above could only ever reply "this panel expired" AFTER a stale click already failed — the buttons themselves stayed visually live forever, since Discord genuinely CAN'T disable a message with zero interaction at all (see `docs/reference/platform-constraints.md`'s button-expiry entry — which is filed there as **the standing refutation of a constraint, not a constraint**: the 15-minute window is a self-imposed BUSINESS rule, never a Discord token limit, and claiming otherwise was wrong twice in one day), which this section makes concrete). Replaced with a real passive mechanism: `utils/passiveExpiry.js`'s `schedulePanelExpiry(interaction, messageId, components)`.
- **Mechanism**: every render of a covered command's panel — the initial slash-command invocation AND every button/select re-render — ends (as of 2026-08-14, inside `sendV2Payload` itself rather than a per-command call) by calling `schedulePanelExpiry` with THAT interaction's own token (each interaction gets its own fresh ~15-minute token, confirmed via Discord's docs and this session's own corrected investigation — see "Known open issues"). It holds a `setTimeout(10 min)` per messageId in an in-memory `Map`; any later interaction on the same message cancels the pending timer and reschedules fresh from ITS OWN token — a genuine **sliding idle window**, not a fixed deadline anchored to creation (the OLD design's explicit choice, now inverted on purpose). If 10 straight minutes pass with no interaction, the timer fires entirely on its own and PATCHes `@original` directly (same raw-REST pattern `sendV2Payload` already uses, bypassing the normal interaction-reply lifecycle) to recursively walk the message's Components V2 tree and set `disabled: true` on every button (type 2) and select (type 3) — no error message, the panel just goes visibly dead.
  - ⚠️ **`skipExpiry` — a PANEL-LEVEL opt-out at the `sendV2Payload` boundary (added 2026-08-17 09:44 EDT, v3.41.0-pre). Four users, and it should stay rare.** `sendV2Payload(interaction, components, { skipExpiry: true })` suppresses the scheduling entirely. It defaults to `false`, so every existing caller is untouched. **The bar is not "losing this panel is inconvenient" — it is "nothing on this panel can go stale."** `/invite` was the first user and qualifies structurally, not by preference: its sole interactive component is a Share Link button whose handler reads nothing from the original interaction and answers with its **own** fresh token, so there is no token-dependent state to expire; and it is the one panel deliberately meant to be found and clicked days later by whoever scrolls past, which is precisely what the idle timer destroys. The dev-only `/embedtest` (2026-10-17) is the second: every control on its render is a `embedtest_dummy:N` that reads no state, and greying them out after ten minutes would change the very design being judged. **View Colors** (the user right-click, 2026-10-19 11:39 EDT) is the third: its only controls are its page buttons, each carrying the subject's id and answered with its own fresh token, and Harkirat asked for "publicly clickable, no timeout". The `/draw calculator` panels (`commands/drawCalculator.js`, `handlers/drawCalc.js`; spec decision 7, 2026-08-27) are the fourth. **Before adding another user, check the panel has no token-dependent component** — a real dashboard (`/settings`, `/manage`, `/colors`) does, and must keep expiring. Note the exemption below is a different mechanism at a different granularity: link buttons are exempt *everywhere*, whereas `skipExpiry` exempts *one panel including its real buttons*.
  - ⚠️ **LINK BUTTONS ARE EXEMPT, both from being disabled AND from arming a timer at all (2026-08-16 21:15 EDT, v3.40.0-pre).** A link button (style 5 / any button carrying a `url`) has no custom_id, fires no interaction and depends on no token, so it can never go stale — disabling it is always wrong. This was a real shipped defect, not a theoretical one: `/help`'s **Website** and **Install Dioreo** buttons were being disabled after 10 minutes alongside its dropdown. `/invite` surfaced it in its sharpest form, because its public panel is link buttons **only** — it armed a timer whose sole effect was to kill the install buttons on a message whose entire purpose is to be clicked later by whoever scrolls past it. **A panel with no non-link interactive component now arms no timer.** `scripts/passiveExpiry.test.js` covers all four cases (link-only arms nothing · link beside a real component still arms · a link survives a disable pass that kills its siblings · a `url` with no `style` is still recognised), and the guard was verified able to FAIL. 10 minutes was chosen as a plain self-imposed UX window, comfortably inside the ~15-minute token ceiling; it is NOT derived from any Discord-side limit.
- **No `fetchReply()` needed even on the very first render** (unlike `dynamicProfile`'s message-id caching, which hit exactly this problem — see `.claude/rules/accent-and-colors.md`) — `sendV2Payload`'s underlying `rest.patch()` call already returns the PATCHed message's own JSON body, and every button/select re-render already carries `interaction.message.id` regardless (used instead, so this works even on `sendV2Payload`'s undeferred single-hop POST path, which returns no body at all — see its own header comment).
- **Every `|{expiresAt}` custom_id segment was removed** (`toggle_*`, `set_*`, `set_page_`, `colors_view` all dropped their trailing segment) along with the 4 reactive `Date.now() > parseInt(expiresAtStr, 10)` checks in the settings handler — Discord itself now refuses a click on an actually-disabled button, so there's nothing left for a reactive check to catch. The author- lock `|userId` segment is untouched on all of them.
- ⚠️ **EXTENDED BOT-WIDE 2026-08-14 — this bullet used to say "scoped to `/settings` only, on purpose" and that is now false.** `/settings` was the reference implementation; the mechanism itself moved into `utils/sendV2Payload.js` (the shared V2 send/patch boundary nearly every command's panel goes through), so every command whose panel renders that way now gets the same rolling 10-minute idle-disable, including the `/colors` panel opened from /settings (`colors_view`; the View Colors right-clicks are exempt, see the `skipExpiry` bullet above) — the "View Colors has NO timeout of its own" claim this bullet used to make is also retired. `commands/settings.js`'s own explicit `schedulePanelExpiry` call was removed as redundant; the mechanism below is unchanged, only WHERE it's invoked from. See `utils/sendV2Payload.js`'s own header comment for the full reasoning and `scripts/passiveExpiry.test.js` for coverage. ⚠️ **The one documented exception CLOSED 2026-08-14 17:20 EDT** — this bullet used to say `/manage`'s confirm/cancel/undo micro-prompts edited their message via discord.js's raw `interaction.update()` rather than `sendV2Payload`, so they never re-armed their own timer. Stage 2 of the `/manage` decomposition (`docs/superpowers/specs/2026-08-14-manage-slash-decomposition-design.md`) replaced all ~25 of those call sites with `handlers/manage/shared.js`'s `prompt()` helper, which routes through `sendV2Payload` like every other panel render — so they now get real passive-expiry scheduling too. `handlers/router.js` still carries the cancel-only safety net it used while that gap was open, kept (not deleted) pending a live click-test that confirms the V2-rendered prompts behave correctly — see that file's own comment on the block and `docs/db-deferred-list.md`'s LIVE CLICK-TEST OWED entry.
- **In-memory only, keyed by messageId** — a bot restart mid-countdown just loses that one pending timer (the panel silently stays clickable a bit longer than intended, never shorter, and the next genuine `/settings` render re-arms it normally). Accepted at this scale per Harkirat's explicit call, not worth a persistent store for a 10-minute UX nicety.

### Admin override on the per-user panel locks (2026-07-18, v2 quick-wins batch)
Harkirat (`ALLOWED_ADMIN_ID`) was getting the same "not your panel" denial as any random third party the moment he clicked a component on someone else's `/settings` or View Colors message (e.g. one made public via Show Everyone, or while investigating a live bug report) — every one of the 7 per-user author-lock sites (`toggle_`, generic `set_`, `set_page_`, `colors_view`, `colors_page_`, `colors_subpage_`, `colors_refresh_`) checked `interaction.user.id !== targetUserId` with no exception. **`/manage`'s own admin-only guard needed no change at all** — it already only ever lets `ALLOWED_ADMIN_ID` through, there's no "someone else's panel" concept for a single shared admin panel.
- **The critical constraint (Harkirat's explicit spec): the override must NOT swap in Harkirat's own data.** Every one of these panels is already keyed by whichever discordId is embedded in the custom_id (`targetUserId`) for DB reads/writes, but several call sites downstream also re-derive that same person's LIVE profile data straight off `interaction.user` (avatar/banner URL, username, createdAt — `settings.js`, `utils/colorPalette.js`'s `getSourceImageInfo`) — simply relaxing the identity check to `!== targetUserId && !== ALLOWED_ADMIN_ID` without also fixing what `.user` resolves to would have silently rendered Harkirat's own avatar/banner/prefs on someone else's panel the moment he clicked through.
- **Fix: `utils/interactionContext.js`'s `resolvePanelActor(interaction, targetUserId)`** returns the discord.js User object callers should treat as "whose data is this" — `interaction.user` unchanged for the normal same-user case, a fresh `interaction.client.users.fetch(targetUserId)` (never cached/guessed) when Harkirat is overriding someone else's panel, or `null` to deny a genuine non-admin. Callers only build a synthetic interaction (via the existing `buildSyntheticInteraction`, overriding just `.user`) when the returned user differs from `interaction.user` — the ordinary same-user path is completely unchanged, zero extra overhead. `deferReply()`/`deferUpdate()`/`sendV2Payload()` all stay on the REAL interaction throughout (they only need token/applicationId, identical either way) — only the calls that actually read `.user` to decide whose data to show (`settingsCommand.execute(...)`, `getPalettePanelData(...)`, `avatarThumbnailUrl`) get the swapped-user synthetic.
- **Every "action blocked" denial message was reworded the same session** (bundled in since it's the same code) — clearer, a little lighter, and says what to do instead, e.g. `/manage`'s admin-only guard now reads "🔒 **This one's admin-only.** ... try any of the bot's public commands instead!" and the `/settings`/View Colors locks read "🔒 **Not your dashboard!** ... run `/settings` yourself" / "🔒 **Those aren't your colors!** Run `/colors` ...". Deliberately light, not the "bully broke people" gag (that's still reserved for its own future personality pass, see `docs/ROADMAP.md`) — this was just a plain clarity/tone pass.

## `open:` — the jump-to option (2026-10-19 17:51 EDT)
`/settings open:Visibility|Preferences|Colors|Stats` lands on page 1, lands on page 2, opens Your Stats (page 2 internally, added 2026-10-20 19:50 EDT), or opens the View Colors panel without going through the dashboard (docs/ROADMAP.md's "/settings jump-to options"). Per-invocation only, never saved. Shipped as `customize:` (v3.93.0) and renamed `open:` 2026-10-19 19:33 EDT (Harkirat): the choice says which page opens, so the old name described something it does not do.
- **It is read only on a real slash invocation** (`isChatInputCommand()`), so every button re-render (`toggle_`/`set_`/`set_page_`) still draws the page its handler asked for. A re-render reading the option would pin the panel to one page.
- **`Colors` goes through `commands/colors.js`'s own `execute()`** with `{ prefsField: 'settingsVisibility' }`, not a third copy of the palette render. ⚠️ `settingsVisibility` is deliberate: this option is a shortcut to the dashboard's View Colors button, and that button reads `settingsVisibility` (see `handlers/colors.js`'s `colors_view` branch). An explicit `visibility:` on the same `/settings` call still wins, because /colors reads the option of that name.
- Covered by `scripts/settingsJumpTo.test.js`, which runs the real `execute()` with the database and the send stubbed.

## "Dioreo User Since" — `firstCommandAt` (2026-10-20 17:55 EDT)
`/settings` shows when the user first ran a command of their own (Harkirat: "start tracking that"). It is the dashboard's only date line since 2026-10-23: the Discord account's "Member Since" was dropped (Harkirat: keep the bot-user line, "how long you've been using the bot"), and `scripts/settingsJumpTo.test.js` asserts it stays gone. `UserPreference.firstCommandAt` is written by `utils/firstCommand.js`, reached through `utils/userStats.js`'s `noteOwnCommand`, which `handlers/router.js` runs AFTER a slash or right-click command; buttons, selects and modals never count, so using someone else's panel does not. Tested by `scripts/firstCommand.test.js`.
- **After, not before:** a first-time user's command may create their record with find-then-save, and an upsert racing that save would fail it with a duplicate key.
- **`$min`, never `$set`:** the date only moves earlier, so the backfill (`scripts/backfillFirstCommandAt.js`, from each record's ObjectId time, an approximation either way) and live writes can run in any order.
- On someone's very first `/settings` the field is not written yet, so a slash invocation shows "now"; a button re-render with no date shows no line.
