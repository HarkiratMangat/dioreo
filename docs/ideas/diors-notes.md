## 🔑 Legend
*How this file's own marks work, decided 2026-07-18, reorganized 2026-07-24 (Harkirat flagged his own
edit-pass to this section was a raw dump, not properly organized — see the filing note in `docs/archive/graveyard.md` for
what changed and why). Read this before adding to, reading, or acting on anything below.*

**The marks:**
- **`[x] ✓ ~~text~~`** — closed, and it SHIPPED / got a real answer. Rendered GREEN (`#3fb950`) in MarkEdit.
- **`[x] ✗ ~~text~~`** — closed, but ABANDONED / dropped / turned out not to be a real issue. Rendered RED (`#f85149`).
- A checked box `[x]` always means **closed** — the ✓/✗ is what tells you HOW it closed, never whether it's still open. (An unchecked box would misleadingly read as "still open" for something dead, which is why `[-]` got retired.) All coloring is `editor.js`'s live MarkEdit-only rendering layer — see "Outside MarkEdit" below.
- **A still-open item — including one that's been filed to its real home but not yet built — is always `- [ ]`, never a bare `-`.** Added 2026-08-03 19:37 EDT (Harkirat's catch): a bare `-` reads as a stray note rather than a tracked open item, and a `<!-- FILED -->` comment is not itself a visual open/closed signal. Filing something is not building it — the box stays unchecked until it actually ships.

**Two dates per resolved item, never conflate them:**
- **`(date)` right after the ✓/✗ mark** — the day AND time Claude actually MARKED the item off (checked the box). Format: `[x] ✓ [YYYY-MM-DD HH:MM TZ] ~~text~~` — always both date and time, never a bare date (a bare date can't disambiguate same-day marks).
- **The date inside the item's own HTML comment** — when the real-world thing actually happened (built, answered, discussed, abandoned). Can differ from the mark-date — e.g. something built 4 days ago might only get checked off today.

**Confirmation mark — Harkirat's own "I've seen this, sort it whenever" signal, never Claude's to add:**
- Added right AFTER `[x]` and BEFORE the ✓/✗ mark — e.g. `[x] ✴︎ ✓ (date) ~~text~~` — placed there because the cursor lands at a fixed, predictable spot right after `[x]` on every line (Harkirat's own reasoning, 2026-07-18), rather than needing to click precisely after wherever ✓/✗ happens to sit.
- Means: "I've read this item and I'm fine with you sorting it (filing it out, sweeping it out to `docs/archive/graveyard.md`) whenever you're ready."
- **An item is NEVER swept out to `docs/archive/graveyard.md` without this mark present, however long it's sat checked off.**
- Symbol + color are switchable live from MarkEdit's own "Confirmation Mark" menu. **The current symbol shortlist, color palette, and exact hex values live in the `reference_markedit_extension_api` memory file, not here** — that file is the one that actually gets updated when the extension changes (this Legend's own copy of that list had already drifted stale — it still listed Pink `#f472b6` as live after Pink was removed 2026-07-19 to avoid clashing with the newer follow-up mark's rose color — which is exactly the failure mode of keeping implementation specifics in two places). This Legend's job is to explain what the marks MEAN; the memory file is the source of truth for their current exact spec.
- **History (2026-07-24→25, condensed):** this Legend originally covered only the ℋ confirmation mark; Harkirat asked for a second, Claude-directed follow-up mark so open questions could be tracked the same way, plus a one-physical-line-per-comment rule (now stated below) and an auto-timestamp on every mark insert. All three shipped 2026-07-25 (rose `#e0708a`, `∴...∵` pair, auto-stamps `[YYYY-MM-DD HH:MM TZ]`) and are live-verified. Full build history: `reference_markedit_extension_api` memory.
- **Claude's own follow-up-mark referencing rule (added 2026-07-24 18:07 EDT, still unverified):** when writing about the follow-up mark in prose, spell it out ("the follow-up mark") instead of using the bare glyph, to avoid accidentally opening/closing a styled region — the extension's real escape/parsing behavior for the bare glyph has never been confirmed, so treat this as a standing caution rather than a proven-safe workaround.
- **WHEN CLAUDE ACTS ON ONE OF HARKIRAT'S FOLLOW-UPS, CLAUDE REPLIES WITH THE CLAUDE-DIRECTED FOLLOW-UP MARK — not with a comment alone (added 2026-07-29 18:24 EDT after this went wrong twice).** The two mark types do different jobs and are not interchangeable: **a comment is reasoning, explanation, and record** — it explains an item; **the follow-up marks are the direct back-and-forth conversation layer on top of everything else**, which is why they carry their own colour and have no placement restrictions. So an answered follow-up gets *at least a one-liner* follow-up-mark reply, even when the substance lives in a comment below — in which case the reply's job is to POINT AT that comment. The reason is concrete rather than stylistic: a comment carries the timestamp of whenever it was written, so **a comment dated in the past cannot tell Harkirat whether it is a fresh reply or something that has been sitting there for days.** That is exactly what happened on the MarkEdit Return-key item — his 2026-07-29 09:32 EDT follow-up was actioned, the comment directly beneath it was from 2026-07-20, and there was no way to tell the difference by looking. Same failure was already flagged 2026-07-24 17:51 EDT. Silently actioning a follow-up and leaving no mark is the thing to stop doing.

**Claude's own comment-writing rules** (the HTML comment attached to a resolved item):
- One continuous physical line per comment — let MarkEdit's own soft-wrap handle display, don't hard-break a sentence across lines. A real bulleted list is the one exception (one bullet per line), with a blank line before the next item's own comment.
- Format: `<!-- WHAT YOU DID <the real-world date, even if in the past> (Claude): your comment, one line. -->`
- **The lead verb is standardized, not free choice (added 2026-08-03 19:40 EDT — Harkirat's catch: "RESOLVED" reads right for a bug, "IMPLEMENTED" for a feature, and the file had been mixing both across item types with no rule).** Pick by what actually happened, in this order:
  - **FIXED** — a confirmed bug got corrected.
  - **IMPLEMENTED** (built, not yet released) or **SHIPPED** (built AND out in a tagged version) — new capability, feature, or extension work. Prefer SHIPPED once a real version number covers it.
  - **ANSWERED** — a question got a real answer; nothing in the codebase changed.
  - **FILED** — routed to its real home (ROADMAP / db-deferred-list / meta-deferred-list) but not built — pair with `- [ ]`, never `[x]` (see the checkbox rule above).
  - **ADOPTED** — a workflow/process suggestion was agreed to and is now standing practice.
  - **REORGANIZED** — existing content restructured; nothing new was added or built.
  - **REVIEWED** — something (a proposal, a doc, an idea) was evaluated and given a real verdict, without necessarily building or changing anything as a result.
  - **DEFERRED** — discussed on purpose and deliberately not acted on yet; leave the item unchecked, not `[x]`.
  - Comments written before 2026-08-03 predate this convention and are left as-is — their meaning is still clear from context, and rewriting ~100 historical comments for word-choice consistency isn't worth the risk of corrupting an otherwise-accurate record. Apply the convention going forward only.

**Outside MarkEdit:** every mark in this file is PLAIN TEXT to any other tool (GitHub, `cat`, another
editor) — the colors are a local MarkEdit-only rendering layer, never baked into the committed characters.
