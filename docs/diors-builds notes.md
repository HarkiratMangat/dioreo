## 🔑 Legend
*How this file's own marks work, decided 2026-07-18 after Harkirat flagged the old system had a real gap. Read this before adding to, reading, or acting on anything below.*

- **`[x] ✓ (date) ~~text~~`** — closed, and it SHIPPED / got a real answer. Rendered GREEN in MarkEdit (`editor.js`'s live coloring — this is a rendering-only layer; the file itself stays plain, unstyled text everywhere else, including on GitHub).
- **`[x] ✗ (date) ~~text~~`** — closed, but ABANDONED / dropped / turned out not to be a real issue. Rendered RED. A checked box always means "closed" — the ✓/✗ is what tells you HOW it closed, never whether it's still open (an unchecked box would misleadingly read as "still open" for something dead, which is why `[-]` got retired earlier).
- **`(date)` right after the ✓/✗ mark** — the day Claude actually MARKED the item off (checked the box), which can be a different day than when the underlying work happened. That second date — when something was built, answered, or discussed — still lives inside the item's own HTML comment, same as always; the two are allowed to differ (e.g. something built 4 days ago might only get checked off today).
- **Confirmation mark — one of 4 candidates, switchable, not a single fixed pick.** Added right AFTER `[x]` and BEFORE the ✓/✗ mark by HARKIRAT ONLY, never by Claude — `[x] ✴︎ ✓ (date) ~~text~~` (using the current default; shortlist below). Placement decided 2026-07-18 (Harkirat: easier to append in practice, since the cursor lands at a fixed, predictable spot right after `[x]` on every line, rather than needing to click precisely after wherever ✓/✗ happens to sit). Means "I've read this item and I'm fine with you sorting it (filing it out, sweeping it to the Graveyard) whenever you're ready." **An item is NEVER swept to the Graveyard without this mark present, however long it's sat checked off.**
- **The 4 shortlisted symbols — ✴︎ eight-point star, ✦ black four-point star, ◆ black diamond, ℋ script H — and 8 FINAL colors (2026-07-18, after several rounds against a 15-candidate artifact) — muted amber `#e3b341`, orange `#fb923c`, pink `#f472b6`, violet `#a78bfa`, periwinkle `#818cf8`, cobalt blue `#3b82f6`, cyan `#22d3ee`, turquoise `#14b8a6` — are all live at once, switchable from MarkEdit's own menu bar** ("Confirmation Mark" menu: Insert Confirmation Mark, Insert at Bullet Front, Insert Check/Cross, Update All Existing Marks to Current Default, Default Symbol, Default Color, Add Toolbar Button…), built 2026-07-18 in `editor.js` + `scripts/markedit-dior-confirm.js` (MarkEdit's own extension folder, NOT this repo) — v2 same day after real bugs found live: a toolbar-button routing mismatch, and symbols only coloring once a full `[x] ... ✓` context existed. **Color changes and the bulk "Update All Existing Marks" action both apply LIVE, no restart** (all MarkEdit extension scripts share one JS global, `window.__diorConfirm__`, same trick `markedit-theme-zero.js` already uses) — only adding the toolbar BUTTON itself still needs a restart, since that's a genuine MarkEdit toolbar-structure reload, not a coloring/text change. Switching the default SYMBOL only affects new inserts; "Update All Existing Marks" is a separate one-click action for retroactively rewriting what's already in the document (replaced an earlier toggle-based design per Harkirat's own suggestion — simpler, no hidden state to forget about).
- Every mark in this file is PLAIN TEXT to any tool other than MarkEdit-with-`editor.js` (GitHub, `cat`, another editor) — the colors are a local rendering layer only, never baked into the actual characters that get committed.
