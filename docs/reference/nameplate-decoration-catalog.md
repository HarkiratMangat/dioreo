# Nameplate/decoration catalog — the source data file

*Read this before writing code against `nameplate-decoration-catalog.json`, and before treating a diff of it as either "new items" or "noise."*

## What the JSON file is

`docs/reference/nameplate-decoration-catalog.json` is a hand-produced, complete snapshot of Discord's entire nameplate + decoration collectibles catalog, authored by Harkirat outside this repo and dropped in here on 2026-08-15 00:55 EDT. It is **not** scraped or generated by any script in this codebase — there is no build step that produces it, so an out-of-date copy stays out of date until someone replaces it by hand or a future sync script is written (see "Keeping it fresh" below).

It was renamed from its original filename `all-nameplates-decorations.json` to `nameplate-decoration-catalog.json` on 2026-08-15 01:00 EDT to match this repo's naming conventions (kebab-case, noun-first) and to pair cleanly with this doc.

**Why it lives in `docs/reference/`, tracked in git, rather than in the gitignored `local/`:** Harkirat wants this data synced to the repo specifically so that a future replacement of this file produces a real `git diff` — which nameplates/decorations Discord added, renamed, or re-paletted becomes visible for free, and it lets a bulk-cache script compare "what the catalog says exists" against "what our own Cloudinary/Discord-storage-channel cache already has."

## Verified structure

Checked by parsing the file programmatically on 2026-08-15 01:00 EDT, not sampled by eye:

- **88 top-level collections** (e.g. `"Underworld"`, `"Solar Eclipse"`, `"Sunkissed"`, `"Palworld"`, `"Toy Story"`), each holding a `nameplates` array and a `decorations` array of design groups.
- **235 nameplate design groups → 262 total SKUs (variants).**
- **490 decoration design groups → 663 total SKUs (variants).**
- **925 SKUs total, 0 duplicate `sku_id` values anywhere in the file.**
- Every nameplate variant carries `palette` + `palette_hex` — 0 of 262 missing either field.
- No decoration variant carries `palette`/`palette_hex` — decorations have no bed/palette concept, confirmed 0 exceptions.
- The `name` vs. `variant_label`/`variant_value` split is 100% consistent across all 925 entries: a single-variant group's one variant carries `name` (the plain design name); a multi-variant group's variants each carry `variant_label` + `variant_value` instead, never both — 0 exceptions found.

### Shape

```
{
  "<Collection Name>": {
    "nameplates": [
      {
        "group_name": "<design name>",
        "base_sku_id": "<sku of the first/default variant>",
        "variants": [
          {
            "sku_id": "<unique per-variant sku>",
            "asset": "nameplates/<slug>/<sku-or-name>/",   // always 3 path segments
            "label": "<Discord's own descriptive caption>",
            "palette": "<one of a 12-entry enum, e.g. \"cobalt\">",
            "palette_hex": "<hex, e.g. \"#0131c2\">",
            // present only on a design that HAS color variants:
            "variant_label": "<Discord's name for this color, e.g. \"Blue\">",
            "variant_value": "<hex, e.g. \"#79e4e3\">"
            // present only on a design with NO variants (single sku):
            "name": "<the design's plain display name>"
          }
        ]
      }
    ],
    "decorations": [ /* same variants[] shape, minus palette/palette_hex */ ]
  }
}
```

### The two colors are unrelated

A nameplate variant can carry both `palette_hex` and `variant_value` at once, and they usually differ: `palette_hex` is the CSS-gradient **bed** behind the nameplate (this matches `utils/nameplatePalettes.js`'s existing 12-entry table exactly — cross-verified for both Twilight `#0131c2`/cobalt and Cat Beans `#730bc8`/violet). `variant_value` is the color identity of the **art itself** on a design that ships in multiple colorways. Eternal Damnation's bed is always black (`#000000`) regardless of which flame-color variant you're looking at — that's the two fields in practice.

### Display-name rule

For a variant carrying `variant_label`, its display name is `"<group_name> (<variant_label>)"`. Re-derived from the raw data and checked, not assumed:

- "Lord of the Dead (Blue)" — `variant_value #79e4e3` (decoration)
- "Lord of the Dead (Red)" — `variant_value #fb515a` (decoration)
- "Eternal Damnation (Blue)" — `variant_value #79e4e3` (nameplate)
- "Astrolabe (Gold)" — `variant_value #f2b329` (decoration)
- "Cycling Lights (RGB)" — `variant_value #c30909` (nameplate)

## Fetching the actual asset

The `sku_id` is the only identifier that matters for fetching — the `asset` slug path is informational, not required:

```
https://cdn.discordapp.com/media/v1/collectibles-shop/{sku_id}/static    → art PNG
https://cdn.discordapp.com/media/v1/collectibles-shop/{sku_id}/video     → art WEBM
https://cdn.discordapp.com/media/v1/collectibles-shop/{sku_id}/animated  → real APNG
```

Live-verified 2026-08-15 against two SKUs pulled directly from this file: Twilight (`1349849614198505602`) and Cat Beans (`1349849614143979540`) both return genuine multi-frame APNGs from `/animated` (confirmed via the PNG `acTL` chunk). This SKU-addressed route is separate from — and strictly better than — the slug-based `assets/collectibles/nameplates/nameplates/{slug}/static.png` route this codebase already uses in `utils/accentColor.js`/`utils/guildProfile.js`: that older route has no animated variant (404 in every form tried) and needs slug parsing this route doesn't.

## Keeping it fresh

`scripts/syncNameplateCatalog.py` fetches Discord's live `collectibles-categories/v2` endpoint and additively merges anything genuinely new into this file — existing entries are never rewritten or removed, and a run that finds nothing new leaves the file byte-identical (no spurious diff). Run it manually from the repo root:

```
python3 scripts/syncNameplateCatalog.py            # fetch, merge, write
python3 scripts/syncNameplateCatalog.py --dry-run   # fetch, report, don't write
```

**This endpoint requires a Discord USER token, not a bot token — verified live 2026-08-15 01:37 EDT.** `Bot <token>` (both `api/v9` and `api/v10`) returns a hard `403 {"code": 20001, "message": "Bots cannot use this endpoint"}`; there is no bot-token substitute. A user token calling a private client API to automate fetches is Discord's definition of "self-botting," which their ToS prohibits for account automation — this is read-only, low-volume, and only touches public storefront data, but it's still that category. **For exactly that reason, this is deliberately NOT scheduled anywhere (no cron, no launchd) — Harkirat runs it by hand when he wants a refresh (2026-08-15 01:42 EDT), specifically so it never becomes standing account automation.**

Credentials (token, session cookie, installation id, client fingerprint) live in the gitignored `scripts/.env.discord-sync` (matches the repo's blanket `.env.*` pattern — never committed). These are session-scoped and **will expire** (cookie/`cf_clearance`/token rotate); when the script starts failing with an HTTP error, pull fresh values from a real Discord desktop-client request (devtools Network tab, any `discord.com/api` call while the shop UI is open) and overwrite that file. The script writes a blank template there on first run if the file is missing.

## Where this feeds into

This file is the bootstrap data for the bulk-cache pipeline: `scripts/syncCatalogToMongo.js` flattens it into one `models/CollectibleCatalog.js` Mongo doc per SKU (git-diffable JSON stays the source of truth; Mongo is a derived runtime index), and `scripts/bulkCacheCollectibles.js` renders every SKU into the bot's existing Cloudinary + Discord-storage-channel pipeline (`utils/nameplateWebpCache.js`, `utils/decorationWebpCache.js`), replacing today's lazy per-user-equip discovery for anything already catalogued — the lazy path stays as the fallback for anything not (yet) in this file, flagged in both Cloudinary context and the cache-channel message as `render_source: 'fallback'` so a later catalog refresh can find and heal it. This supersedes the frozen `docs/superpowers/specs/2026-08-09-nameplate-decoration-animated-gif-caching-design.md`'s "don't precompute the whole catalog" argument by explicit decision (2026-08-15 10:46 EDT) — that spec anticipated a hypothetical; a real 925-entry catalog existing now is a materially different situation.

⚠️ **Both nameplates and decorations now render from the SKU-addressed `/animated` endpoint above**, not `/video` — pivoted 2026-08-15 10:31 EDT once the endpoint was confirmed to return a genuine multi-frame APNG for nameplates too (previously nameplates sourced from the slug-based `asset.webm` route, needing ffmpeg's `-c:v libvpx-vp9` flag to force real alpha decoding; that workaround is gone now that both kinds share the same simpler `-f apng` extraction). See `utils/nameplateWebpCache.js`'s header for the full pipeline history.

🚧 **The full 925-SKU run against the PROD bot is a v3 pre-launch blocker, not scheduled to this pipeline's build session** — the prod bot currently has no access to the "dioreoland" storage server, and fixing that means enabling guild-install on the prod app, which would also let real users guild-install the live bot early (undesired before v3 launches). See `docs/db-deferred-list.md`. The pipeline itself is fully built and verified against the dev bot; pointing it at prod is a config change (the two `*_CACHE_CHANNEL_ID` env vars + the invite), not a code change.
